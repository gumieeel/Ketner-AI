# Канал Telegram для клиентов бизнеса (проект, без кода)

Статус: проект на ревью, 23.11.2026. Кода в этом PR нет.

Решение владельца от 23.11.2026: Telegram возвращается в двух ролях.

1. **Уведомления владельцу** — через существующего бота Ketner. Это уже работает: предупреждения
   об объёме тарифа и поломках подключений, а с PR #80 — новые заявки.
2. **Канал для клиентов бизнеса** — этот документ. Бизнес создаёт **своего** бота в BotFather и
   подключает его к Ketner. Сообщения клиентов идут через исполнение Ketner, как на странице бота, и
   считаются обращениями тарифа.

---

## 1. Что видит владелец

1. **Кабинет бота → «Каналы» → «Telegram».** Короткая инструкция:
   - откройте @BotFather → `/newbot`;
   - придумайте имя и адрес;
   - скопируйте токен.
2. **Поле «Токен бота»** (`123456789:AA…`) и кнопка «Подключить».
3. **Ketner проверяет токен.** Вызывает `getMe` и показывает: «Бот @shop_bot подключён. Напишите ему
   в Telegram — ответит ваш бот Ketner».
4. **Карточка канала.** Адрес `t.me/shop_bot`, QR, состояние (раздел 9), «Отключить».

**Один бот Telegram — одно решение Ketner.** Подключить тот же токен ко второму решению нельзя: в
базе уникален `telegram_bot_id`, его возвращает `getMe`. Ко всем остальным частям решения канал
добавляется так же, как страница и виджет: тот же агент, те же знания, заявки, автоматизации.

## 2. Хранение токена

**Таблица `telegram_channels`** — отдельный SQL на одобрение владельцу, в `migration-list.ts` только
после одобрения:

| Поле                            | Что                                                                                           |
| ------------------------------- | --------------------------------------------------------------------------------------------- |
| `id`                            | uuid канала                                                                                   |
| `user_id`, `solution_id`        | владелец и решение (каскад при удалении)                                                      |
| `telegram_bot_id`               | числовой id бота из `getMe`, **уникален**                                                     |
| `username`                      | `@shop_bot`, для карточки                                                                     |
| `token_enc`                     | токен, зашифрованный `sealToken(…, 'telegram-bot-token')`, формат `v1.…` (CHECK как у Google) |
| `webhook_secret_hash`           | sha256 секрета вебхука (раздел 3); сам секрет не хранится                                     |
| `status`                        | `connected / token_invalid / disconnected`                                                    |
| `last_error_code`, `last_ok_at` | как у `google_connections`                                                                    |
| `connected_at`, `updated_at`    |                                                                                               |

**Шифрование** — `platform/token-crypto.ts`, новое назначение `telegram-bot-token`:

- ключ `sha256('ketner:telegram-bot-token:' + BETTER_AUTH_SECRET)` — свой, отдельный от GitHub и
  Google;
- смена `BETTER_AUTH_SECRET` делает токен нечитаемым → `token_invalid`, владельцу письмо и
  Telegram «подключите бота снова» (как у Google);
- токен не попадает в ответы API, логи, журнал исполнений, ошибки, Sentry;
- в логах — только `telegram_bot_id` и код ошибки.

## 3. Вебхук на каждого бота

- **Адрес:** `POST /api/telegram/channel/<channelId>`. Регистрируется при подключении:
  `setWebhook(url, secret_token, allowed_updates=["message"], max_connections=10, drop_pending_updates=true)`.
- **Секрет:** у каждого канала свой. `secret_token` — 32 случайных байта (base64url, Telegram
  допускает `A-Za-z0-9_-` до 256 символов). В базе только хеш. Запрос без заголовка
  `X-Telegram-Bot-Api-Secret-Token` или с неверным → `401`, тело не читается. Так же устроен
  нынешний вебхук бота Ketner (`routes/telegram.ts`), только секрет общий.
- **Ответ Telegram — сразу `200`.** Обработка идёт в фоне. Если ответить позже 60 секунд или с
  ошибкой, Telegram повторит отправку, а ответ модели может идти дольше.
- **Повторы и дубли:** `update_id` пишется в журнал исполнений как ключ идемпотентности
  (`idempotency_key = tg:<channelId>:<update_id>`), повтор того же обновления → `duplicate`, второго
  ответа нет.
- **Что принимается в v1:** текстовые `message` из личного чата (`chat.type = private`). Группы,
  каналы, фото, голос, файлы и стикеры получают вежливый ответ «Я понимаю только текст» без вызова
  модели и без обращения. `edited_message`, `callback_query` и прочие обновления не подписаны.
- **Ответ клиенту:** `sendMessage` от имени бота клиента, `parse_mode` не используется (обычный
  текст, без HTML — нечего экранировать). Кнопки частых вопросов — `reply_markup.keyboard`.

## 4. Разговор и форма заявки

- **Посетитель** — `tg:<chat.id>` вместо `visitorId` браузера. Разговор — один на
  (канал, chat.id), продолжается, пока клиент пишет. «Новый диалог» — команда `/start`.
- **Агент тот же** (`bot-agent.ts`, путь платформы), канал в `AgentSpec` — новый вид
  `telegram` (`{ kind: 'telegram', channelId }`). Эскалации и правила формы из `contact-policy.ts`
  (#74) работают так же.
- **Форма заявки** в Telegram — короткий диалог вместо формы. Бот спрашивает «Как к вам
  обращаться?» и «Телефон или @ник для связи» и предлагает кнопку «Поделиться номером»
  (`request_contact`). Заявка создаётся тем же `createLead`, `contact` — телефон или
  `@username`, если клиент разрешил. Отказ («Нет, спасибо») ничего не сохраняет.
- **Заявка запускает те же автоматизации:** таблица, уведомление менеджеру.

## 5. Ограничения частоты

| Что                         | Ограничение                                                  | Зачем                                           |
| --------------------------- | ------------------------------------------------------------ | ----------------------------------------------- |
| Сообщений от одного chat.id | 20 за 10 минут (как `perVisitor` страницы бота)              | одна переписка не съедает объём тарифа          |
| Сообщений на канал          | 600 за 10 минут                                              | всплеск или атака на один бот                   |
| Заявок от одного chat.id    | 5 в час (как `leadsPerAddress`)                              | спам заявками                                   |
| Длина сообщения             | 1000 символов, остальное отрезается с пометкой               | как на странице бота                            |
| Исходящие в Telegram        | не больше 1 сообщения в секунду в чат, ~25 в секунду на бота | лимиты Bot API; при `429` — ждать `retry_after` |

При превышении клиент получает одно сообщение «Слишком много сообщений подряд. Подождите несколько
минут», дальше бот молчит до конца окна. Модель не вызывается, обращения нет.

## 6. Обращения и тариф

- **Обращение** — исполнение с `trigger_kind = 'channel_event'`. Оно уже в списке считаемых
  (SUBSCRIPTION_PRICING_DESIGN, 5.1), правило счётчика не меняется: `succeeded`, не `failures`,
  модель вызывалась.
- **Не считаются:**
  - ответы без модели — «понимаю только текст», ограничение частоты, режим заявок;
  - вопросы формы заявки;
  - `/start` без вопроса.
- **Перед ответом** — то же решение, что на странице бота (5.2): тариф и меньше 110% — ответ модели;
  иначе — режим заявок: «Сейчас я не могу ответить сам. Оставьте имя и телефон…» и диалог заявки.
- **Канал — внешний сервис или нет** — открытый вопрос владельцу (BUILDER_V1, раздел 8).
  Рекомендация ревьюера — **нет**, считать только системы данных. Пока не решено, лимит сервисов
  на подключение канала не проверяется.

## 7. Тариф закончился или решение выключено

- **Тариф не активен или решение выключено:** вебхук остаётся, токен хранится. Бот отвечает без
  модели: «Сейчас бот не отвечает. Оставьте имя и телефон — вам перезвонят» и ведёт диалог заявки.
  Так клиент не теряется, как на странице бота. Заявки и уведомления владельцу работают.
- **Тариф снова активен** — ответы модели возобновляются сами, без переподключения.
- **Решение удалено** — канал отключается (раздел 8), вебхук снимается.
- **Аккаунт удалён** — регистрация в `eraseAccount`: `deleteWebhook` по возможности, строка
  `telegram_channels` удаляется, разговоры и заявки — по существующим правилам. Сам бот в Telegram
  принадлежит владельцу, Ketner его не удаляет (и не может).

## 8. Отключение и отзыв токена

- **«Отключить» в Ketner:**
  1. `deleteWebhook(drop_pending_updates=true)` по возможности — сбой только в лог;
  2. `token_enc = NULL`, `status = disconnected`;
  3. бот в Telegram перестаёт отвечать.

  Повторное подключение — тот же токен или новый.

- **Владелец сменил токен в BotFather** (`/revoke`): старый токен недействителен, Telegram вернёт
  `401 Unauthorized` на первый `sendMessage`. Тогда:
  - `status = token_invalid`;
  - владельцу письмо и Telegram (бот Ketner): «Токен бота @shop_bot больше не действует —
    подключите бота снова с новым токеном»;
  - вебхук на старом токене больше не приходит.
- **Владелец удалил бота в BotFather** — то же, что смена токена.
- **Кто-то подключил тот же бот к другому сервису:** `setWebhook` там снимает наш вебхук,
  обновления перестают приходить. Ketner раз в сутки проверяет `getWebhookInfo` и, если адрес чужой,
  ставит `status = token_invalid` с кодом `webhook_taken` и сообщает владельцу.

## 9. Состояние на карточке

| Состояние                            | Карточка                                                         | Действие                                      |
| ------------------------------------ | ---------------------------------------------------------------- | --------------------------------------------- |
| `connected`                          | «@shop_bot отвечает клиентам», последний ответ: …                | Отключить                                     |
| `token_invalid`                      | «Токен больше не действует (сменили в BotFather или бот удалён)» | Ввести новый токен · Отключить                |
| `token_invalid`, код `webhook_taken` | «Бот подключён к другому сервису — Ketner не получает сообщения» | Подключить снова (вернуть вебхук) · Отключить |
| `disconnected`                       | «Не подключён»                                                   | Подключить                                    |

## 10. Приватность

**Что получает Ketner:**

- chat.id, имя и @username клиента из Telegram;
- текст сообщений;
- телефон — только если клиент сам нажал «Поделиться номером».

**Хранение:**

- разговоры и заявки — как на странице бота;
- срок хранения и удаление — по разделу 9 политики конфиденциальности;
- chat.id хранится в разговоре, пока он есть.

**Политика конфиденциальности, раздел 8:**

- пункт «Telegram — канал вашего бота: сообщения ваших клиентов вашему боту Telegram идут через
  Ketner»;
- данные клиентов бизнеса Ketner обрабатывает по поручению владельца бота (как уже сказано в
  разделе 2 политики).

**Владелец бота** отвечает за свою политику для клиентов. Ketner даёт текст-заготовку для описания
бота в BotFather: «Отвечает ИИ. Данные обрабатываются сервисом Ketner AI по поручению <бизнеса>».

## 11. Тесты (для PR с кодом)

- **Подключение:**
  - `getMe` → карточка;
  - неверный токен → отказ без сохранения;
  - тот же бот ко второму решению → `409`;
  - токен в ответах и логах не появляется.
- **Вебхук:**
  - без секрета или с чужим → `401`;
  - повтор `update_id` → один ответ;
  - группа, фото → «понимаю только текст» без модели.
- **Тариф:** обращение считается как `channel_event`; при 110% и без тарифа — диалог заявки без
  модели.
- **Частота:** 21-е сообщение за 10 минут → одно предупреждение, дальше тишина.
- **Отключение:** `deleteWebhook` вызван, токен стёрт.
- **Поломки:** `401` на `sendMessage` → `token_invalid` и одно уведомление; суточная проверка
  `getWebhookInfo` → `webhook_taken`.
- **Удаление аккаунта:** строка удалена, отзыв вебхука по возможности.

## 12. Порядок работы (каждый — отдельный PR, без слияния до ревью)

1. SQL `telegram_channels` в `docs/` на одобрение владельцу (без `migration-list.ts`).
2. После одобрения:
   - миграция;
   - `token-crypto` назначение `telegram-bot-token`;
   - хранилище;
   - подключение и отключение, без вебхука;
   - флаг выпуска выключен.
3. Вебхук и разговор:
   - приём, идемпотентность, ответ агента;
   - диалог заявки;
   - частота;
   - тариф.
4. Карточка в кабинете (в мастере — карточка шага 3, BUILDER_V1), поломки и уведомления.
5. Политика конфиденциальности и пилот на аккаунте владельца, как у Google Таблиц (5a → 5b).
