## 1. Рамки лицензии

### 1.1. Что говорят лицензия и FAQ n8n

Sustainable Use License 1.0 разрешает использование «только для внутренних деловых целей» или некоммерческое. Файлы `.ee.` требуют Enterprise-лицензии. Официальный FAQ уточняет (дословно):

- «Build automations for your clients on your instance, as long as your clients do not have the possibility to create or edit them».
- «Charge your customers for workflow creation, setup, and maintenance services».
- «Use n8n behind the scenes in your own product, where users can use and trigger the automations you built, and even connect their own accounts to them».
- «Triggering or executing pre-built workflows via API or webhooks is fine».
- Нельзя: «Allow external end users to build or configure their own workflows through your product, whether via a custom UI, our API, MCP, or an AI agent acting on the user's behalf».
- Критерий: «who controls the workflow logic».

### 1.2. Режимы Ketner

| --- | ------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

- **Данные (можно задавать клиенту и ИИ Ketner, после проверки схемой):** входные значения запуска — текст, адрес чата, номер строки таблицы, время напоминания, выбор подключения из своих.
- **Логика (только сотрудники Ketner):** узлы, связи, условия, выражения, сохранённые параметры узлов, расписание и триггеры процесса.

Отдельный вопрос к n8n — подписка «Автоматизации» и пример «Automation-as-a-service» из FAQ. Письмо — [LICENSE_INQUIRIES.md](LICENSE_INQUIRIES.md), раздел 1.

### 1.3. Следствия для продукта

- Discovery и Solution Builder **выбирают** готовый процесс из каталога и заполняют входные данные по схеме. Они не генерируют и не меняют процессы n8n.
- Каталог процессов ведёт команда Ketner: исходник — в Ketner (версия, автор, кто одобрил); импорт в n8n — только адаптером из одобренной версии.
- Ни один клиентский API Ketner не принимает и не возвращает определения процессов n8n.

## 2. Изоляция клиентов: обеспечивает Ketner, а не n8n

В Community Edition нет проектов и общего доступа к процессам и учётным данным. Все процессы и учётные данные всех клиентов принадлежат одному владельцу n8n. **n8n не знает о клиентах Ketner и не разделяет их.** Изоляция целиком — на стороне Ketner.

### 2.1. Сопоставления (в базе Ketner)

| Таблица (проект)          | Ключевые поля                                                                                                     | Правило                                                                                                                                      |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `workflow_templates`      | id, версия, исходник процесса, схема входных данных, нужные виды подключений, статус одобрения, кто одобрил       | Общие для всех; без данных клиентов                                                                                                          |
| `workflow_deployments`    | id, `user_id`, шаблон и версия, режим (M1/M2/M3/M4), `n8n_workflow_id` (уникально), секрет и путь вебхука, статус | Клиент ↔ процесс n8n. Один `n8n_workflow_id` принадлежит ровно одному владельцу (кроме общих M2 без подключений клиента — владелец `ketner`) |
| `integration_connections` | id, `user_id`, провайдер, `n8n_credential_id` (уникально), статус, дата проверки, дата отзыва                     | Клиент ↔ учётные данные n8n. Сам секрет в Ketner не хранится — только ссылка на объект в n8n                                                 |
| `workflow_runs`           | id, `user_id`, развёртывание, `n8n_execution_id`, статус, стоимость, ошибка                                       | Каждый запуск привязан к владельцу до вызова n8n                                                                                             |

Ketner никогда не определяет владельца по имени или тегу объекта в n8n — только по своим таблицам. Объекты в n8n получают имена из непрозрачных id Ketner без email и названий бизнеса.

### 2.2. Правила

1. **API n8n — только из бэкенда.** Ключ `N8N_API_KEY` есть только у `ketner-ai`, вызовы — только из адаптера `workflows/n8n`. Ни один ответ сайту не содержит адресов n8n, ключей и определений процессов.
2. **Проверка перед каждым запуском:** запрашивающий владеет развёртыванием; развёртывание активно; все подключения процесса принадлежат тому же `user_id` и действительны; бюджет и лимиты не превышены; для действий риска HIGH есть одобрение.
3. **Проверка перед импортом (M4):** каждый id учётных данных в процессе есть в `integration_connections` того же `user_id`. Иначе импорт отклоняется.
4. **Вебхук процесса** доступен только из внутренней сети и требует секрет развёртывания (Header Auth). Секреты у развёртываний разные.
5. **Ответ из n8n** приходит с одноразовым токеном исполнения, привязанным к (`user_id`, развёртывание, запуск). Токен от другого запуска отклоняется.
6. **Внешние вебхуки:** маршрут `/api/automation-hooks/:id` → развёртывание → владелец; подпись провайдера проверяется до пересылки.
7. **Клиенту — никакого доступа к n8n:** ни учётной записи, ни адреса, ни API.

### 2.3. Жизненный цикл учётных данных

| Этап              | Что происходит                                                                                                                                                                                                                                                                   |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Подключение       | Клиент вводит ключ в форме Ketner (или выдаёт доступ сервисному аккаунту Ketner). Ketner создаёт учётные данные через `POST /credentials`, проверяет их `POST /credentials/{id}/test`, сохраняет только `n8n_credential_id`. Секрет не пишется в логи, журналы, промпты и знания |
| Использование     | Только процессы этого же клиента (правило 3)                                                                                                                                                                                                                                     |
| Замена            | Новые учётные данные → переключение развёртываний → удаление старых                                                                                                                                                                                                              |
| Отключение        | Деактивация процессов, которые их используют (`GET /credentials/{id}/dependencies`), затем `DELETE /credentials/{id}`; статус «отозвано»                                                                                                                                         |
| Удаление аккаунта | Деактивация и удаление всех процессов клиента, его учётных данных и запусков (`DELETE /executions/{id}`) в n8n; проверка по таблицам сопоставлений, что объектов не осталось                                                                                                     |

### 2.4. Учётные данные и OAuth: проверено опытом на n8n 2.46.6

Проверка 07–08.11.2026 на одноразовом локальном стенде `n8nio/n8n:2.46.6` (SQLite, без внешних сервисов) с тестовым OAuth2-провайдером. Провайдер настоящий по протоколу: выдаёт код, токены доступа и обновления, ротирует refresh-токен, защищает ресурс и умеет «просрочить» токен. Стенд удалён после проверки. Сверено с исходниками тега `n8n@2.46.6`.

| #   | Что проверялось                                        | Путь в n8n                                                                                                                                                                 | Документированный публичный API?                                                                                                                                                                                                                                                        | Результат                                                                                                                                                                                                                                                                                                                                           |
| --- | ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | CRUD учётных данных                                    | `POST/GET/PATCH/DELETE /api/v1/credentials`, `GET /api/v1/credentials/schema/{type}`, `POST /api/v1/credentials/{id}/test`, `GET /api/v1/credentials/{id}/dependencies`    | Да                                                                                                                                                                                                                                                                                      | Работает. Данные проверяются по схеме типа, лишние поля отклоняются                                                                                                                                                                                                                                                                                 |
| 2   | Создание OAuth2-учётных данных с действующими токенами | `POST /api/v1/credentials`, тип `oAuth2Api`, `data.oauthTokenData = { access_token, refresh_token, token_type, expires_in }` от провайдера                                 | Да: путь документирован, а поле `oauthTokenData` (тип `json`) возвращает документированный `GET /credentials/schema/oAuth2Api`. n8n сам добавляет его в свойства `oAuth1Api`/`oAuth2Api` (`CredentialsHelper.getCredentialsProperties`). Отдельного описания поля в справочнике API нет | **Работает:** 200, токены сохранены в точности                                                                                                                                                                                                                                                                                                      |
| 3   | Использование и обновление токена                      | Процесс, созданный и опубликованный через публичный API (`POST /api/v1/workflows`, `POST /api/v1/workflows/{id}/activate`): вебхук → HTTP Request с этими учётными данными | Да                                                                                                                                                                                                                                                                                      | **Работает.** Запрос с переданным токеном. После «просрочки» провайдер ответил 401, n8n сам обменял переданный refresh-токен (`grant_type=refresh_token`), повторил запрос (200) и сохранил новый access-токен и новый, ротированный refresh-токен (видно в расшифрованной выгрузке). Следующий запуск — с новым токеном, без повторного обновления |
| 4   | Авторизация и колбэк самого n8n                        | `GET /rest/oauth2-credential/auth` → провайдер → `GET /rest/oauth2-credential/callback`                                                                                    | **Нет** — внутренние пути редактора, нужна сессия владельца                                                                                                                                                                                                                             | Работает, но `redirect_uri` = колбэк самого n8n: браузер должен попасть на n8n. Токены сохранены, n8n добавил `n8n_expires_at`. Повтор колбэка без сессии отклонён (n8n записал «OAuth2 callback failed», хотя ответил страницей со статусом 200)                                                                                                   |

Выводы:

- **Схема для Ketner:** авторизацию и обмен кода проводит Ketner на своём адресе (`ketner.org`, OAuth-приложение — Ketner). Готовые токены передаются в n8n документированным `POST /api/v1/credentials` (опыт 2). Обновляет токены сам n8n (опыт 3). Ketner токены у себя не хранит: после обновления в n8n его копия устарела бы.
- **Внутренние пути редактора (опыт 4) в production не используются:** они не входят в публичный API, требуют сессии владельца и публичного адреса n8n.
- **Ограничения:**
  - у переданных токенов нет `n8n_expires_at`, поэтому n8n обновляет их по ответу 401 (`tokenExpiredStatusCode`), а не заранее. Провайдеры, которые на просроченный токен отвечают не 401, требуют настройки этого кода или передачи `n8n_expires_at` — проверить для каждого провайдера при подключении;
  - для OAuth2 `POST /credentials/{id}/test` ответил «Connection Successful!» и на фиктивный токен: к провайдеру он не ходит и подлинность подключения не доказывает. Проверка подключения — первым запуском или запросом Ketner к провайдеру;
  - поведение закреплено за версией 2.46.6: обновление образа — только после повторения опытов 2–3 контрактным тестом адаптера;
  - активация процесса через API регистрирует вебхук не мгновенно: первый вызов сразу после `activate` вернул 404, повтор — 200. Адаптер ждёт регистрации (проверка с повтором), а не считает 404 ошибкой процесса. `POST /workflows/{id}/activate` в 2.46.6 помечен устаревшим, вместо него — `POST /workflows/{id}/publish`.
- **Если поведение опытов 2–3 изменится в новой версии** — запасные варианты без недокументированных путей:
  1. ключи и сервисные аккаунты (Telegram — токен бота, почта — SMTP/IMAP, Google — сервисный аккаунт Ketner, HTTP с ключом) — для них OAuth не нужен;
  2. запросы к OAuth-сервисам делает инструмент Ketner своими токенами, а процесс n8n вызывает этот инструмент через API Ketner;
  3. остаться на закреплённой версии n8n до решения.

**Права API-ключа.** В 2.46.6 Community Edition права выбираются при создании ключа (в списке 109) и соблюдаются: ключ только с `credential:*` получил 403 на `GET /api/v1/executions` и 200 на `GET /api/v1/credentials`. Ключ Ketner выпускается только с нужными правами: процессы, запуски, учётные данные, без пользователей, пакетов и аудита. Сам ключ создаётся человеком в интерфейсе n8n один раз при настройке; на стенде он выпускался через сессию редактора только для опытов.

### 2.5. Тесты изоляции (обязательны до production)

- Пользователь B не запускает, не останавливает и не видит развёртывание и запуски пользователя A — по прямому id тоже.
- Импорт процесса с учётными данными другого пользователя отклоняется.
- Ответ из n8n с токеном запуска A не меняет запуск B.
- Внешний вебхук A не попадает в процесс B.
- После отключения подключения и после удаления аккаунта в n8n не остаётся объектов клиента (контрактный тест на локальном n8n).
- Ответы API Ketner не содержат секретов, адресов и id объектов n8n.
- Статическая проверка запросов к таблицам сопоставлений (как в [PLATFORM_ARCHITECTURE.md](PLATFORM_ARCHITECTURE.md), раздел 3).

## 3. Сетевая схема

### 3.1. Сравнение

| Критерий                  | A. Публичный Web Service за Cloudflare Access                                                                                                                                                                                                                  | B. Private Service + вход через Ketner                                                                                   |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Что видно из интернета    | Домен редактора (`n8n-admin.ketner.org`); `*.onrender.com` отключается `renderSubdomainPolicy: disabled`                                                                                                                                                       | Ничего: у сервиса нет публичного адреса                                                                                  |
| Защита редактора          | Cloudflare Access + вход n8n с 2FA. Риск: Cloudflare Access защищает, только если запрос идёт через Cloudflare. n8n не проверяет токен Access, поэтому прямой запрос к Render с этим доменом в обход Cloudflare нужно исключить отдельно — проверить на стенде | Не нужна: редактора в production нет                                                                                     |
| Внешние вебхуки           | Через Ketner (так или иначе — ради проверок)                                                                                                                                                                                                                   | Через Ketner — единственный путь                                                                                         |
| Сборка процессов командой | Прямо в production-редакторе                                                                                                                                                                                                                                   | В локальном n8n (Docker у сотрудника), экспорт → каталог Ketner → одобрение → импорт адаптером                           |
| Отладка в production      | Редактор и история запусков                                                                                                                                                                                                                                    | Через Ketner: журнал запусков + `GET /executions/{id}` адаптером (админка Ketner); воспроизведение — на локальном стенде |
| OAuth-колбэки n8n         | Возможны, но требуют захода клиента на n8n — не используем; токены передаёт Ketner через API (раздел 2.4)                                                                                                                                                      | Невозможны — не используем                                                                                               |
| Дисциплина изменений      | Возможна «правка на лету» в production мимо каталога                                                                                                                                                                                                           | Любое изменение — только новой версией из каталога: история, одобрение, откат                                            |
| Стоимость                 | Одинакова по инстансу; Cloudflare Access до 50 пользователей бесплатен                                                                                                                                                                                         | Одинакова по инстансу                                                                                                    |

### 3.2. Рекомендация: B — Private Service

Почему:

- В n8n лежат учётные данные всех клиентов, а в Community Edition один владелец и нет SSO. Самая безопасная поверхность — отсутствие публичного адреса.
- Схема B совпадает с рамками лицензии и с правилом «исходник процесса — в Ketner»: менять процесс можно только через каталог с одобрением, без ручных правок в production.
- У A есть риск обхода Cloudflare Access прямым запросом к Render. Его нужно отдельно закрывать и проверять.

Что придётся принять:

- Нет production-редактора. Процессы собираются в локальном n8n той же версии; это нужно оформить как процедуру (Docker-команда, экспорт, проверка, импорт).
- Отладка — через журнал Ketner и данные запусков с ошибкой (`EXECUTIONS_DATA_SAVE_ON_ERROR=all`). Тяжёлые случаи воспроизводятся на стенде.
- В админке Ketner понадобятся экраны «каталог процессов» и «запуски» (задачи T6.7, T9.1).
- Если позже понадобится production-редактор, переход на A — смена типа сервиса и домена. Процессы, база и адаптер при этом не меняются.

## 4. Сервисы и ресурсы

```
Интернет
  │
  └─ ketner.org (Cloudflare) ──► Render Web: ketner-ai (существующий, план не меняется)
                                    │  сайт, API, вход внешних вебхуков /api/automation-hooks/:id
                                    │  проверки: подпись, размер, частота, владелец, бюджет
                                    │
                                    │  внутренняя сеть Render (тот же регион)
                                    ▼
                         Render Private Service (Docker): ketner-n8n
                            /api/v1  ← только ketner-ai, X-N8N-API-KEY
                            /webhook ← только ketner-ai, секрет развёртывания
                                    │
                                    ▼
                         Render Postgres: ketner-n8n-db (только для n8n)

  Supabase Postgres (существующий): данные Ketner — у n8n нет доступа
```

| Сервис             | Тип Render                                                                                                                                                                    | Пилот                    | Рекомендуется         | Основание                                                            |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------ | --------------------- | -------------------------------------------------------------------- |
| `ketner-n8n`       | Private Service, образ `n8nio/n8n:2.46.6` с Docker Hub или `docker.n8n.io/n8nio/n8n:2.46.6` (закреплён; из среды проверки `docker.n8n.io` не открылся, Docker Hub — открылся) | Starter: 0,5 CPU, 512 МБ | Standard: 1 CPU, 2 ГБ | В документации n8n — 320 МБ–2 ГБ памяти; 512 МБ — без запаса на пики |
| `ketner-n8n-db`    | Render Postgres 17                                                                                                                                                            | Basic-256mb              | Basic-1gb             | Короткая история запусков (раздел 5)                                 |
| `ketner-ai`        | существующий Web Service                                                                                                                                                      | без изменений            | без изменений         | Уже не на Free (по словам владельца)                                 |
| Redis, воркеры n8n | —                                                                                                                                                                             | не нужны                 | не нужны              | Queue mode — только при заметной нагрузке                            |

Почему отдельная база: n8n поддерживает PostgreSQL 16–18 (версию Supabase-проекта Ketner нужно проверить); учётные данные клиентов в n8n не делят базу и логин с данными Ketner; бэкапы и нагрузка — раздельно.

## 5. Стоимость (только прирост)

Прирост — два новых ресурса. План `ketner-ai` не меняется. Цены — сторонние обзоры Render 2026 года, **сверить на render.com/pricing**, в том числе что Private Service стоит столько же, сколько Web Service того же размера:

| Позиция                        | Пилот     | Рекомендуется |
| ------------------------------ | --------- | ------------- |
| `ketner-n8n` (Private Service) | $7        | $25           |
| `ketner-n8n-db`                | $6        | $19           |
| **Прирост в месяц**            | **≈ $13** | **≈ $44**     |

Не входит: фоновый воркер Ketner для очереди агентов (T1.4) — ≈ $7, когда понадобится; возможная плата за рабочее пространство Render — уже есть в текущем счёте и от n8n не меняется. Cloudflare Access при варианте B не нужен.

## 6. Настройки безопасности n8n

Задаются в Environment сервиса `ketner-n8n`. Секреты — только там, не в `render.yaml` и не в git.

| Переменная                                                                        | Значение                                                                         | Зачем                                                                                                 |
| --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `DB_TYPE`                                                                         | `postgresdb`                                                                     | Postgres вместо SQLite                                                                                |
| `DB_POSTGRESDB_HOST/PORT/DATABASE/USER/PASSWORD`                                  | из `ketner-n8n-db`, внутренний адрес                                             | Подключение только по внутренней сети                                                                 |
| `N8N_ENCRYPTION_KEY`                                                              | случайные 32+ байта, **секрет**                                                  | Шифрует учётные данные. Копия — в менеджере паролей владельца; без неё учётные данные не восстановить |
| `N8N_PORT`                                                                        | порт, на который Render направляет трафик приватного сервиса                     | —                                                                                                     |
| `N8N_WEBHOOK_URL`                                                                 | `https://ketner.org/api/automation-hooks/` — **после** реализации входа в Ketner | Триггеры, которые сами регистрируют вебхук (например, Telegram), получают адрес Ketner                |
| `N8N_PUBLIC_API_SWAGGERUI_DISABLED`                                               | `true`                                                                           | Без площадки API                                                                                      |
| `N8N_DIAGNOSTICS_ENABLED`, `N8N_PERSONALIZATION_ENABLED`, `N8N_TEMPLATES_ENABLED` | `false`                                                                          | Без телеметрии, опросов и внешних шаблонов                                                            |
| `N8N_COMMUNITY_PACKAGES_ENABLED`                                                  | `false`                                                                          | Без сторонних узлов                                                                                   |
| `NODES_INCLUDE`                                                                   | список разрешённых узлов (ниже); запасной вариант — `NODES_EXCLUDE`              | Загружаются только разрешённые узлы                                                                   |
| `N8N_BLOCK_ENV_ACCESS_IN_NODE`                                                    | `true`                                                                           | Выражения не читают окружение (ключ шифрования, пароль базы)                                          |
| `N8N_BLOCK_FILE_ACCESS_TO_N8N_FILES`                                              | `true`                                                                           | Нет доступа к файлам `.n8n`                                                                           |
| `N8N_SSRF_PROTECTION_ENABLED`                                                     | `true`; `N8N_SSRF_ALLOWED_HOSTNAMES` — только внутренний адрес Ketner            | HTTP-узлы не ходят во внутреннюю сеть, кроме Ketner                                                   |
| `N8N_MFA_ENABLED`                                                                 | `true`                                                                           | 2FA для владельца (вход нужен только при первичной настройке и на стенде)                             |
| `EXECUTIONS_TIMEOUT`, `EXECUTIONS_TIMEOUT_MAX`                                    | `300`, `900`                                                                     | Потолок длительности запуска                                                                          |
| `EXECUTIONS_DATA_SAVE_ON_SUCCESS`                                                 | `none`                                                                           | Успешные запуски не хранят данные клиентов                                                            |
| `EXECUTIONS_DATA_SAVE_ON_ERROR`                                                   | `all`                                                                            | Данные ошибок — для отладки через Ketner                                                              |
| `EXECUTIONS_DATA_MAX_AGE`, `EXECUTIONS_DATA_PRUNE_MAX_COUNT`                      | `168` (7 дней), `5000`                                                           | Короткое хранение                                                                                     |
| `GENERIC_TIMEZONE`                                                                | часовой пояс по умолчанию                                                        | Расписания                                                                                            |

**Разрешённые узлы для старта** (точные имена типов сверить на стенде): Webhook, Respond to Webhook, HTTP Request, If, Switch, Edit Fields (Set), Merge, Schedule Trigger, Wait, No Operation, Error Trigger, Stop and Error, Date & Time, Telegram, Google Sheets, Send Email.

**Запрещены всегда:** Code, Execute Command, Read/Write Files from Disk, Local File Trigger, SSH, FTP, Git, Execute Workflow, все AI/LangChain-узлы, узел n8n API. Модели вызываются только через Ketner (HTTP-запрос с одноразовым токеном исполнения → AIGateway → учёт и списание).

**Ключ API n8n:** в 2.46.6 Community Edition права ключа выбираются при создании и соблюдаются (проверено на стенде, раздел 2.4). Ключ Ketner — только с правами на процессы, запуски и учётные данные; хранится только в `ketner-ai` (`N8N_API_KEY`), со сроком действия, ротация при подозрении на утечку; каждый вызов адаптера пишется в журнал Ketner.

**Бэкапы:** исходники процессов — в каталоге Ketner; база `ketner-n8n-db` — бэкапы Render (проверить состав для выбранного плана); `N8N_ENCRYPTION_KEY` хранится отдельно от бэкапа базы. Восстановление проверяется на стенде.

**Обновления:** образ закреплён; новая версия — сначала на локальном стенде с контрактными тестами адаптера, затем в production с бэкапом перед обновлением.
