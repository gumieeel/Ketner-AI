# Продуктовая архитектура: Ketner AI как платформа решений

Целевое устройство после трансформации, проект от 30.10.2026, решения владельца внесены в тот же день. Опирается на [PROJECT_AUDIT.md](PROJECT_AUDIT.md); порядок работ — [MIGRATION_PLAN.md](MIGRATION_PLAN.md). Всё ниже — предложение для согласования: числа лимитов, выбор моделей и цены этапов уточняются замерами.

## 1. Пользовательский путь

Пользователь начинает с задачи, а не с модели. Путь и то, что на каждом шаге делает система:

| Шаг                       | Что видит пользователь            | Что делает Ketner                                     | Вызов модели    |
| ------------------------- | --------------------------------- | ----------------------------------------------------- | --------------- |
| 1. Цель                   | Поле «Опишите задачу…» на главной | Создаёт анализ                                        | —               |
| 2. Анализ контекста       | «Разбираю задачу»                 | Context Analyzer: структура контекста и пробелы       | 1               |
| 3. Уточнения              | До 3 вопросов, можно пропустить   | Сохраняет ответы                                      | —               |
| 4. Поиск возможностей     | «Ищу возможности»                 | Discovery Engine                                      | 1               |
| 5. Проверка реализуемости | Статус у каждой возможности       | Feasibility Engine по каталогу возможностей платформы | — (код)         |
| 6. Оценка пользы          | Польза с допущениями              | Impact Estimator по данным пользователя               | — (код)         |
| 7. Отчёт                  | Резюме, возможности, первые шаги  | Сохраняет отчёт                                       | —               |
| 8. План                   | Шаги со статусами                 | Plan Generator для выбранной возможности              | 1               |
| 9. Решение                | Ketner Builder: настройка         | Создаёт решение из возможности                        | —               |
| 10. Тест                  | Прогон тест-кейсов                | Запуски решения, проверки                             | по числу тестов |
| 11. Использование         | Решение `active`                  | Запуски на реальных данных                            | по запускам     |

Итого типичный анализ — 2 вызова модели, план — ещё 1. Feasibility и Impact считает код: модель не решает, что Ketner умеет, и не придумывает цифры.

Чат с моделями, Ketner Code, картинки и `/v1` остаются отдельными разделами.

## 2. Модули сервера

Все модули — внутри `apps/mock-api/src`, вызовы моделей только через существующий `AIGateway.stream` со служебной задачей `task`.

```
routes/analyses.ts ─┐                      ┌─ discovery/context-analyzer.ts ─┐
routes/plans.ts ────┼─ discovery/service.ts ┼─ discovery/discovery-engine.ts ├─ discovery/run-task.ts ─ AIGateway.stream
routes/solutions.ts ┘  builder/service.ts   ├─ discovery/plan-generator.ts ──┘   (task.kind, учёт, кредиты)
                                            ├─ discovery/feasibility.ts ── discovery/capabilities.ts
                                            └─ discovery/impact.ts
          хранилища: discovery/store.ts, builder/store.ts (Postgres; в памяти — локально и в тестах)
```

### Общий вызов модели — `discovery/run-task.ts`

- Принимает: пользователя (из сессии), вид задачи, системный промпт этапа, пользовательские данные, схему ответа, бюджет `maxCostUsd`.
- Вызывает `AIGateway.stream` с `task: { kind, id, systemPrompt, templateOutput }`, собирает текст из `onDelta`.
- Разбирает `extractJsonObject` (из `services/answer-review.ts`) и проверяет схемой. Невалидно — один повтор с описанием ошибки разбора; снова невалидно — ошибка этапа `model_output_invalid`, кредиты за неудачный вызов уже списаны шлюзом и видны в учёте.
- Ничего не делает в обход шлюза: выбор модели, fallback, предохранитель, сторож, цена, списание и учёт — штатные.

### A. Context Analyzer — `discovery/context-analyzer.ts`

Вход: текст задачи (до 8 000 символов), язык, ответы на вопросы. Выход (схема `AnalysisContext`):

| Поле                 | Тип                                                                    | Что                                                          |
| -------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------ |
| `domain`             | строка                                                                 | область деятельности                                         |
| `goals`              | строки                                                                 | цели                                                         |
| `tasks`              | `{ title, frequency?, timeSpent? }[]`                                  | задачи; частота и время — только если пользователь их назвал |
| `recurringProcesses` | `{ title, steps[] }[]`                                                 | повторяющиеся процессы                                       |
| `tools`              | строки                                                                 | текущие инструменты                                          |
| `constraints`        | строки                                                                 | ограничения (бюджет, данные, законы)                         |
| `availableData`      | строки                                                                 | доступные данные                                             |
| `missing`            | `{ field, why }[]`                                                     | чего не хватает                                              |
| `questions`          | `{ id, text, reason, optional, kind: 'text' \| 'choice', options? }[]` | до 3 вопросов, только те, что меняют результат               |

Каждое значение помечается `source: 'user' | 'inferred'`: в отчёте предположения показываются как предположения.

### B. Discovery Engine — `discovery/discovery-engine.ts`

Вход: `AnalysisContext` и ответы. Выход: 3–7 возможностей:

| Поле                                      | Что                                                                           |
| ----------------------------------------- | ----------------------------------------------------------------------------- |
| `title`, `problem`, `solution`            | название, исходная проблема своими словами пользователя, предлагаемое решение |
| `requires`                                | id из каталога возможностей (`capabilities.ts`); незнакомые id отбрасываются  |
| `dataNeeded`, `integrationsNeeded`        | какие данные и подключения нужны                                              |
| `effort`                                  | `low` / `medium` / `high` с объяснением                                       |
| `risks`, `limitations`, `successCriteria` | риски, ограничения, критерии успеха                                           |
| `impactInputs`                            | что нужно для оценки пользы: какая задача, сколько раз, сколько времени       |

### C. Feasibility Engine — `discovery/feasibility.ts` (код, без модели)

Статус считается по каталогу возможностей платформы. Модель статус не выставляет и повысить его не может.

| Статус              | Правило                                                                                                                                  |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `ready`             | все `requires` доступны сейчас без настройки                                                                                             |
| `needs_setup`       | нужна настройка внутри Ketner: создать решение, загрузить данные, купить кредиты для API-ключа                                           |
| `needs_integration` | нужно подключение, которое Ketner поддерживает, но у пользователя его нет (сейчас — только GitHub)                                       |
| `not_supported`     | нужна возможность, которой у Ketner нет (например, CRM, почта пользователя, расписание, веб-поиск); в отчёте — что можно сделать вручную |

Каталог `discovery/capabilities.ts` — проверяемый код, а не текст промпта. Начальный состав (по коду на 30.10.2026):

| id                                                                                      | Возможность                                          | Сейчас                           |
| --------------------------------------------------------------------------------------- | ---------------------------------------------------- | -------------------------------- |
| `text_generation`                                                                       | ответы и тексты моделями чата                        | доступно                         |
| `document_text`                                                                         | текст из TXT, DOCX, XLSX, PPTX                       | доступно                         |
| `pdf_reading`                                                                           | чтение PDF                                           | нет                              |
| `vision`                                                                                | разбор изображений моделью                           | нет                              |
| `web_search`                                                                            | поиск в интернете                                    | нет                              |
| `image_generation`                                                                      | генерация картинок                                   | доступно                         |
| `code_agent`                                                                            | Ketner Code: правки кода по задаче                   | доступно (без выполнения команд) |
| `github_repo`                                                                           | работа с репозиторием GitHub                         | подключение GitHub               |
| `api_access`                                                                            | OpenAI-совместимый `/v1`                             | после покупки кредитов           |
| `cross_check`                                                                           | проверка ответа моделью другой компании              | доступно                         |
| `scheduled_runs`, `external_actions`, `email`, `crm`, `spreadsheets_sync`, `messengers` | расписание, действия во внешних системах, интеграции | нет                              |

### D. Impact Estimator — `discovery/impact.ts` (код, без модели)

- Числовая оценка только если пользователь сам назвал частоту и время задачи: `экономия в неделю = раз в неделю × минут на раз × доля, которую берёт на себя ИИ`. Доля — допущение с диапазоном (например, 30–60%), показывается как допущение.
- Ответ хранит формулу, исходные числа с пометкой «со слов пользователя», допущения и диапазон «от–до».
- Без исходных чисел — только качественная оценка («снижает ручную работу при подготовке отчётов») и вопрос, какие данные нужны для расчёта.
- Никогда не показывается как фактический результат: подпись «прогноз».

### E. Plan Generator — `discovery/plan-generator.ts`

Вход: контекст, ответы, выбранная возможность с её статусом. Выход: цель, исходные условия, инструменты, подготовка данных, этапы, тестирование, критерии готовности, риски, оценка расходов, ограничения. Шаг: `{ id, title, description, dependsOn[], status: 'todo' | 'in_progress' | 'done' | 'blocked', doneCriteria }`. Сервер проверяет, что `dependsOn` ссылается на шаги этого же плана и нет циклов. Расходы на модели в плане считает код по реестру цен, а не модель.

### Выбор моделей этапов — `discovery/model-policy.ts`

Модели этапов, их цена и стоимость бесплатного анализа для сервиса — в расчёте [discovery-models.md](discovery-models.md); выбор согласуется с владельцем до этапа 2. Правила, которые от расчёта не зависят:

- один этап — один вызов модели; несколько моделей параллельно не запускаются;
- сильная модель — только по явной кнопке «Глубокий анализ» и за кредиты;
- когда кредитов на выбранную модель не хватает, шлюз штатно переходит на модель дешевле или бесплатную;
- судья в тестах решения — модель другой компании (`pickReviewers`).

## 3. Ketner Builder

### Типы решений (первый набор)

| Тип                                                       | Конфигурация                                                                   | Что не умеет                          |
| --------------------------------------------------------- | ------------------------------------------------------------------------------ | ------------------------------------- |
| `assistant` — персональный помощник                       | модель, инструкции, справочный текст до 32 000 символов, формат ответа, язык   | действия во внешних системах          |
| `content` — генерация и обработка контента (позже)        | шаблон с переменными `{{input}}`, формат результата, ограничения длины и стиля | публикация                            |
| `workflow` — простой процесс обработки информации (позже) | 2–5 последовательных шагов «текст → текст», у каждого своя инструкция          | ветвления, расписание, внешние данные |

Первым делается только `assistant` (решение владельца): его можно по-настоящему настроить и проверить тест-кейсами. `content` и `workflow` — после приёмки помощника, на той же модели данных.

Инструментов с внешними действиями у решений нет. Если возможность требует их, она получает `not_supported` или `needs_integration` ещё в отчёте, и Builder объясняет, чего не хватает, вместо имитации.

### Состояния

```
draft → configuring → ready_for_test → testing → active
                           ↑               │  ↘
                           └── (правка) ───┘   failed
active ⇄ paused        любая правка конфигурации → новая версия → ready_for_test
```

- `active` выставляет только сервер: последняя версия прошла все обязательные тест-кейсы и в конфигурации нет ошибок валидации.
- Правка конфигурации `active`-решения создаёт новую версию в статусе `ready_for_test`; рабочей остаётся прежняя версия, пока новая не пройдёт тесты.
- `failed` — тест-кейсы не прошли или запуск завершился ошибкой; переход обратно — после правки или повторного теста.

### Тестирование

- Тест-кейс: вход и проверки. Проверки: `contains`, `not_contains`, `max_length`, `json_valid`, `matches_format`, `judge` (критерий словами; судья — модель другой компании, как в перекрёстной проверке).
- Решение предлагает 2–3 тест-кейса из критериев успеха возможности; пользователь их правит. Проверка на реальных данных — отдельной кнопкой и только после тестов.
- Результат каждого запуска хранится: вход, выход, итог каждой проверки, модель, стоимость.

## 5. API

Анализы и отчёты (`/api/analyses/*`) доступны гостю с `X-Guest-Id` (ограничение по IP, как у гостевого чата); после входа анализ переносится в аккаунт по тому же правилу, что диалоги (`claimGuest…`: только записи гостя этого браузера). Планы с сохранением и решения (`/api/plans/*`, `/api/solutions/*`) требуют входа (`requireAuth`). Ответы и ошибки — в существующем формате `{ error: { code, message } }`. Изменяющие запросы принимают заголовок `Idempotency-Key`. Тела проверяются схемой, чужая запись — `404 not_found` (а не 403, чтобы не раскрывать существование).

## 6. Сайт

| Адрес                                    | Экран                                                                                | Оболочка                               |
| ---------------------------------------- | ------------------------------------------------------------------------------------ | -------------------------------------- |
| `/`                                      | «Что вы хотите улучшить?»: поле, кнопка «Найти возможности», 4 интерактивных примера | компактная верхняя панель, без боковой |
| `/analyses/:id`                          | ход анализа: этапы, вопросы, затем отчёт                                             | верхняя панель                         |
| `/analyses/:id/o/:oppId`                 | подробности возможности, «Создать решение», план                                     | верхняя панель                         |
| `/analyses`                              | сохранённые анализы                                                                  | верхняя панель                         |
| `/solutions`, `/solutions/:id`           | решения; вкладки «Обзор», «Настройки», «Тестирование», «История»                     | верхняя панель                         |
| `/chat`, `/code`, `/images`, `/settings` | как сейчас                                                                           | `AppShell` с боковой панелью           |
| `/models`, `/pricing`                    | принимают разделы прежней главной                                                    | `StandaloneLayout`                     |

- Верхняя панель: логотип, «Анализы», «Решения», «Чат», кредиты, аккаунт. Боковая панель остаётся только в рабочих разделах чата и кода.
- Визуальное направление: текущая тёмная тема (`--canvas #1d1f21`, текст `#eceef0`) и шрифт Geologica подходят; нефрит остаётся в логотипе, основной кнопке и редких акцентах; срезанные углы `corner-shape` сохраняются.
- Состояния каждого экрана: загрузка (скелетон этапов), ошибка с причиной и кнопкой повтора, пустой результат (анализ не нашёл возможностей — что уточнить).
- Прогресс анализа живёт на сервере; черновик текста с главной — в `localStorage`, чтобы пережить вход и перезагрузку.
- Новые тексты — ключи `home.*`, `analysis.*`, `builder.*` в `i18n/ru.ts` и `en.ts`.

## 7. Монетизация и права

- Деньги — существующие кредиты: каждый вызов модели списывается шлюзом по реальной цене. Отдельной валюты, второго механизма списания и цен «за анализ» нет.
- **Один бесплатный анализ в сутки** (решение владельца) — и гостю, и вошедшему, без списания пробных 200 кредитов: его оплачивает сервис. Механизм — признак служебной задачи `task.billing: 'sponsored'`: шлюз не вызывает `CreditService.charge`, но пишет полную себестоимость в учёт с пометкой `sponsored`, чтобы расход сервиса был виден в админке. Бесплатный анализ ограничен суточным бюджетом сервиса и квотой на пользователя (гостю — по guest id и IP). Дополнительные анализы в те же сутки — за кредиты по реальной цене; гостю для них нужен вход.
- Квоты операций — новый модуль `services/discovery-limits.ts` в одном месте с остальными лимитами: анализов в сутки, планов в сутки, решений всего, тестовых прогонов и запусков в сутки, доступ к «Глубокому анализу». Значения по уровням `free` и `credits` не фиксируются до решения владельца; сайт читает их из `plan-facts.json`, совпадение проверяет тест.
- Бесплатный пользователь проходит хотя бы один полный анализ с отчётом: это и есть бесплатный анализ дня.
- Служебные вызовы анализа не съедают 10 сообщений чата в сутки и не блокируются ими (пункт 5 раздела 2 плана), но проходят проверки частоты, параллельности и токенов.
- До запуска этапа сайт показывает оценку в кредитах (по реестру цен), после — фактическую из учёта.

## 8. Безопасность

| Угроза                                                                          | Защита                                                                                                                                                                                                         |
| ------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Чтение и изменение чужих данных                                                 | `user_id` из сессии в каждом запросе к базе; чужая запись — 404; тесты на каждую сущность                                                                                                                      |
| Повторное выполнение и двойное списание                                         | `Idempotency-Key` + уникальный индекс; этап в статусе `running` или `done` не перезапускается; повтор возвращает сохранённый результат                                                                         |
| Prompt injection в описании задачи, ответах, справочном тексте, тестовых данных | Пользовательский текст — отдельным сообщением в разметке `<user_data>`; системный промпт этапа запрещает следовать инструкциям из данных; ответ модели — только данные по схеме, ничего из него не исполняется |
| Вывод модели как команда                                                        | Статусы реализуемости, переходы решения в `active`, цены и квоты считает код; поля ответа модели только отображаются                                                                                           |
| Чрезмерные расходы                                                              | Бюджет `maxCostUsd` на этап и запуск, квоты, штатный потолок остатка кредитов, без параллельных моделей                                                                                                        |
| Злоупотребление лимитами                                                        | `RateLimiter` на пользователя, квоты в учёте, гостевые анализы (если будут) — по IP, как гостевой чат                                                                                                          |
| Некорректные конфигурации                                                       | Схема конфигурации каждого типа решения; модель — только из реестра и включённая; размер полей ограничен                                                                                                       |
| Секреты                                                                         | Решения первого набора секретов не хранят; когда появятся интеграции — шифрование как у `github_connections`, никогда в логах и ответах API                                                                    |
| Действия с последствиями                                                        | В первом наборе их нет; при появлении — подтверждение пользователя на каждое действие и журнал в `solution_runs`                                                                                               |

## 9. Тестирование

- Сервер (`node:test`, `createApp` с хранилищами в памяти и шаблонным движком): схемы и терпимый разбор, каталог и статусы реализуемости, формула пользы, переходы состояний решения, изоляция пользователей, идемпотентность, ошибки модели и невалидный JSON, нехватка кредитов, квоты.
- `templateOutput` у каждой служебной задачи даёт детерминированный JSON для тестов без ключей моделей.
- Сайт (Vitest + `fake-api.ts`): главная и примеры, ход анализа и вопросы, пропуск и правка ответа, восстановление после перезагрузки, отчёт со статусами, Builder: настройка, тест, история.
- Регрессии: существующие наборы чата, сравнения, проверки, Code, оплаты и пререндера проходят без изменений, кроме тестов прежней главной.
