## 2. Решение: арендатор (T0.2)

**Решение:** арендатор — пользователь. Колонка владельца во всех новых таблицах — `user_id text NOT NULL`, как во всех таблицах миграций `0001–0012`.

Почему:

- Организаций, ролей и рабочих пространств в коде нет. Владелец каждой записи — `user_id`, и все проверки доступа в сервисах построены на нём.
- Новое имя колонки (`tenant_id`, `owner_id`) создало бы два соглашения в одной базе без выигрыша.
- В доменных типах TypeScript уже принято `ownerId` (`builder/types.ts`, `discovery/types.ts`). Это соглашение сохраняется.

Путь к организациям, когда они понадобятся:

1. Таблица `workspaces` и членство (`workspace_members`: роль владелец / сотрудник).
2. В таблицы платформы агентов добавляется `workspace_id`, заполняется личным пространством владельца (одна миграция, только добавление).
3. Проверки доступа переходят с `user_id = $1` на «пользователь — член пространства записи». Чтобы это была замена в одном месте, все новые хранилища получают владельца одним параметром (`OwnerScope`), а не собирают условие сами.

Что это значит для задач этапа 1: в схемах и типах — поле `ownerId`; в таблицах — `user_id`; хранилища принимают владельца первым аргументом.

## 3. Решение: изоляция данных и RLS (T0.3)

**Решение:** основная защита остаётся в коде сервера. RLS сейчас не вводим. Для новых таблиц добавляем автоматическую проверку запросов и тест изоляции. К вопросу RLS возвращаемся по условиям ниже.

Что показала проверка кода:

- Сервер ходит в Supabase Postgres одной ролью из `DATABASE_URL` через `postgres.js`. В Supabase это обычно роль `postgres`, которая обходит RLS, поэтому политики без отдельной роли ничего бы не защитили.
- Поправка 08.11.2026: в миграции `0012_implementation_pricing` RLS **включён без политик** для четырёх таблиц сметы. Это закрывает прямой доступ ролей `anon`/`authenticated` через API Supabase, а сервер работает владельцем таблиц и RLS не затрагивается. Все новые таблицы платформы следуют этому же образцу ([PERSISTENCE_DESIGN.md](PERSISTENCE_DESIGN.md)).
- Все запросы к данным клиентов в `builder/`, `discovery/`, `pricing/`, `images/` либо содержат `user_id`, либо проверяют владельца в сервисе. Исключения без владельца намеренные:
  - бот по публичному адресу (`solutions WHERE slug = $1`) и его диалоги — страница `/b/:slug` открыта без входа;
  - картинка по подписанной ссылке (`images/image-store.ts: getById`) — подпись проверяет маршрут;
  - сметы и заявки читаются по id, а владельца сверяет `pricing/service.ts` (`found.userId === userId`);
  - бюджет бесплатных анализов, версии цен, журнал админа — общие или служебные данные;
  - `db/sync.ts` — зеркало хранилищ в памяти, где владелец проверен раньше.
- Изоляцию уже проверяют тесты: `security-regressions.test.ts`, тесты хранилищ (`builder/store.test.ts`, `discovery/store.test.ts`) на Postgres.

Почему не RLS сейчас:

- Нужна отдельная роль без `BYPASSRLS`, а каждый запрос должен идти внутри транзакции с `SET LOCAL app.user_id`. С пулом `postgres.js` это переделка всех хранилищ, а не новая функция.
- Публичные пути (бот, вебхуки, воркер, админка) всё равно требуют обходных ролей. Сложность растёт, а основная защита остаётся в коде.

Что делаем вместо этого (входит в задачи этапа 1):

1. **Проверка запросов в тестах.** Тест читает исходники хранилищ платформы агентов и падает, если `SELECT`/`UPDATE`/`DELETE` к таблице с `user_id` не содержит `user_id` и не стоит в явном списке исключений с причиной.
2. **Тест изоляции на каждую новую таблицу:** второй пользователь не читает, не меняет и не удаляет чужое — по прямому id тоже.
3. **Секреты** (подключения интеграций) хранятся зашифрованными (AES-256-GCM, ключ вне базы). Даже при ошибке в запросе утечка из базы не раскрывает токены.
4. **Журнал действий** для всего, что делает агент или workflow от имени клиента.

Когда вернуться к RLS: появятся организации с ролями; клиентский код начнёт ходить в базу напрямую (Supabase client, Realtime); или появится второй сервис с доступом к тем же таблицам (например, отдельный воркер с другой кодовой базой).

## 4. Решение: инфраструктура (T0.5)

**Сейчас:** один web-сервис Ketner на Render. В `render.yaml` записано `plan: free`, но, по словам владельца, сервис уже не на Free — файл нужно привести к факту отдельной правкой. Таймеры (`setInterval`) и лимиты частоты живут в памяти процесса.

**Решение:** существующий web-сервис Ketner без изменения плана; n8n — отдельный Private Service со своей базой ([N8N_DEPLOYMENT.md](N8N_DEPLOYMENT.md)); позже — процесс-воркер Ketner для очереди агентов.

| Компонент             | Что делает                                                                                                 | Где                                                    |
| --------------------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| Web (как сейчас)      | API, сайт, вход внешних вебхуков (проверяет и ставит задачу или пересылает в n8n)                          | Render, существующий сервис, план не меняется          |
| Воркер (новый)        | Забирает задачи из очереди в Postgres: исполнения агентов, шаги workflow, расписания, повторы, напоминания | Render Background Worker, тот же репозиторий и образ   |
| Postgres              | Данные, очередь задач (`FOR UPDATE SKIP LOCKED`), журнал исполнений                                        | Supabase, как сейчас                                   |
| n8n Community Edition | Исполнение процессов (workflow): триггеры, интеграции, расписания; доступ только из бэкенда Ketner         | Render Private Service (Docker) + своя Render Postgres |

Прирост стоимости (сторонние обзоры цен Render 2026, на render.com не сверено): n8n и его база — около $13 в месяц на пилоте и около $44 в рекомендуемой конфигурации; воркер Ketner — ещё около $7, когда понадобится. Расчёт — [N8N_DEPLOYMENT.md](N8N_DEPLOYMENT.md), раздел 5.

Код воркера можно запускать в том же процессе, что и web (флаг), — так он работает локально и в тестах; отдельный воркер на Render — когда нагрузка этого потребует.

## 5. Целевая архитектура

```
Сайт Ketner (React)
  └─ API Ketner (Express 5, один репозиторий)
       ├─ Discovery (как есть): описание → профиль → возможности
       ├─ Solution Planner: возможность → SolutionSpec → AgentSpec / KetnerWorkflowDefinition
       │     └─ проверки кодом: схема Zod, реестр возможностей, права и риск, бюджет
       ├─ Builder (как есть, расширяется): решения, версии, тест-кейсы, развёртывание, откат
       ├─ Agent Runtime: AgentGateway или Mastra (решение — T4.0) → только через AIGateway
       ├─ Workflow: WorkflowEngineAdapter → адаптер n8n (сейчас) | другие адаптеры (позже, тот же интерфейс)
       ├─ Knowledge Engine: документы и фрагменты в Postgres, полнотекстовый поиск, позже pgvector
       ├─ Integrations: реестр возможностей + подключения с зашифрованными секретами
       ├─ Approvals / Permissions / Budgets: код, а не промпт
       └─ Pricing Engine (как есть, расширяется): смета, бюджеты, факт против оценки
  └─ Воркер (тот же код): очередь в Postgres → исполнения, шаги, расписания, повторы
AIGateway (как есть): единственный путь к моделям, учёт, кредиты, запасные модели
PostgreSQL (Supabase): всё состояние Ketner
n8n Community Edition (отдельный сервис Render, своя Postgres): исполнение процессов, доступ только из Ketner
```

### 5.1. Границы модулей сервера

| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- |

| `agents/`       | Исполнение агента, реестр инструментов, проверка прав перед вызовом, память, запись исполнений                                                                                                                | `ai/gateway.ts`, `ai/agent-gateway.ts`          |
| `workflows/`    | `WorkflowEngineAdapter`, адаптер n8n, прокси внешних вебхуков, каталог готовых процессов                                                                                                                      | `jobs/`, `agents/`                              |

Существующие модули не переписываются: Discovery, Pricing и Builder расширяются через новые функции и поля.

### 5.2. Агенты

- **Спецификация** — `AgentSpec` (Zod): роль, инструкции, разрешённые и запрещённые действия, инструменты, источники знаний, политика модели и памяти, лимиты, эскалация, тесты, версия. Текущие `AssistantConfig` и `BotSettings` переводятся в неё без потерь.
- **Жизненные циклы:** четыре отдельных автомата — решение, развёртывание агента, процесс, запуск процесса. Состояния решения и развёртывания выводятся из существующих записей и сводятся к `draft / active / paused`; переход проверяет сервер ([DOMAIN_MODEL.md](DOMAIN_MODEL.md), раздел 8).
- **Исполнение:** каждый шаг модели — через AIGateway с новым видом задачи (`task.kind: 'agent'`), кредиты списываются как сейчас. Каждое исполнение пишется в журнал: владелец, инициатор, агент и версия, id исполнения и трассы, вход, выход, модель, инструменты, стоимость, длительность, статус, ошибка, одобрение.
- **Инструменты** вызываются только из реестра; права и риск проверяет код до вызова. HIGH — только после одобрения, CRITICAL — запрещено.
- **Mastra или свой цикл** — решает спайк T4.0. Критерии: даёт ли Mastra то, чего нет в `AgentGateway` (память, трассировка, структурированный вывод), не обходя AIGateway, и сколько стоит зависимость (размер, транзитивные пакеты, сборка). Части `ee/` Mastra не используются. Сейчас Mastra и Activepieces в зависимостях отсутствуют (проверено по `package-lock.json`).

### 5.3. Знания

- Таблицы документов и фрагментов с доменом (глобальная библиотека, интеграции, знания клиента, опыт внедрений), владельцем (для знаний клиента), статусом проверки, версией, источником.
- Первая версия — полнотекстовый поиск Postgres (`tsvector`, конфигурации `russian` и `english`, индекс GIN). Векторный поиск (`pgvector`) — только после замера (T3.4); для тестов понадобится образ `pgvector/pgvector:pg16` в CI.
- Найденный текст — данные, не инструкции: отдельный блок промпта, тест с вредоносным документом.
- Ничего не попадает в глобальную библиотеку без одобрения администратора; журналы исполнений и диалоги клиентов не индексируются в общие знания.

### 5.4. Интеграции и подключения

- **Технический реестр** — расширение `discovery/capabilities.ts` (статусы спецификации, операции, триггеры, авторизация, лимиты, тест соединения). Ценовой каталог `pricing/catalog.ts` остаётся отдельным: «можем сделать вручную по заявке» ≠ «платформа умеет сама».
- **Подключение клиента** — запись с зашифрованным секретом (AES-256-GCM, общий модуль из `github/connection-store.ts`), статусом, правами, датой проверки. Секрет не возвращается на сайт, не пишется в логи, не попадает в промпты и знания. Отзыв — одно действие.
- **OAuth** — где сервис его даёт; иначе — ключ с объяснением прав и назначения.

| Требование              | Как обеспечено                                                                                                                                                                                                                                               |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |

### 5.6. Цены и учёт

- Расход моделей — только через AIGateway и `CreditService`, как сейчас; ни агенты, ни workflow не меняют баланс напрямую.
- Бюджеты (на агента, клиента, сутки, месяц, исполнение, число вызовов инструментов) проверяются до запуска и после каждого шага; при превышении — остановка с сохранением состояния и понятная причина.
- Смета решения — расширение `pricing/engine.ts` (разовая цена, подписка, модели, внешние сервисы, сопровождение); модель цену не задаёт.
