# Доменная модель этапа 1: SolutionSpec, AgentSpec, совместимость

Составлено 07.11.2026. Задачи T1.1, T1.2, T1.3 и T1.5 из [TRANSFORMATION_TASKS.md](TRANSFORMATION_TASKS.md). Вторая редакция — по реализации с правками владельца.

Статус — **реализовано в коде без подключения к продукту**: модуль `apps/mock-api/src/platform/` с тестами. Миграций, маршрутов, изменений сайта и инфраструктуры нет; существующие модули не менялись. Ни один маршрут пока не вызывает этот модуль.

## 1. Принципы

1. **Спецификации описывают бизнес-задачу и решение, а не исполнителя.** В `SolutionSpec` и `AgentSpec` нет n8n, его узлов, лицензий, режимов и рантаймов. Та же спецификация валидна при смене исполнителя процессов или рантайма агентов.
2. **Что можно исполнить здесь и сейчас, решает отдельный слой** — `platform/compatibility.ts`: возможности поставщика, лицензия, развёртывание, интеграции, одобрения.
3. **Рантайм агента выбирается отдельной привязкой** — `platform/runtime-binding.ts`. Существующий AgentGateway и Mastra исполняют одну и ту же `AgentSpec`.
4. **Риск выводится из последствий действия**, а одобрение — отдельное правило поверх риска (`platform/risk.ts`).
5. **Хранилище не меняется.** `AgentSpec` и состояния выводятся из существующих записей; переводчики туда и обратно проверены тестами на краевых случаях.
6. **Модель ничего из этого не задаёт:** цены — Pricing Engine (в спецификации только `estimateId`), доступность — реестр возможностей, риск и одобрения — словарь действий, состояния — сервер.
7. **Спецификации не меняют значения:** текст не обрезается (`trim`), чтобы перевод старых настроек был точным. Очистка ответа модели — задача будущих схем черновиков.

## 3. Риск и одобрение

`classifyRisk(consequences)` — по пяти признакам: эффект (`read`, `draft`, `write`, `send`, `delete`, `financial`, `legal`), охват (внутри Ketner или наружу), аудитория (`none`, `single`, `bulk`), обратимость, значимость (`routine`, `significant`).

| Пример                                    | Риск            |
| ----------------------------------------- | --------------- |
| Внутренний черновик                       | LOW             |
| Обычное обратимое изменение записи в CRM  | LOW             |
| Значимое или необратимое изменение записи | MEDIUM          |
| Сообщение одному клиенту                  | MEDIUM          |
| Уведомление владельцу                     | LOW             |
| Рассылка, массовое изменение данных       | HIGH            |
| Обратимое изменение денег (цены)          | HIGH            |
| Удаление: обратимое / необратимое         | HIGH / CRITICAL |
| Возврат денег, подписание договора        | CRITICAL        |

Словарь действий (`ACTIONS`): `knowledge.search`, `reply.draft`, `reply.send_in_session`, `lead.create`, `owner.notify`, `record.update`, `record.update_significant`, `message.send`, `message.bulk_send`, `record.delete`, `payment.refund`, `price.change`, `contract.sign`. Риск каждого действия **выводится** из его последствий, а не записан руками; тест сверяет ожидаемые значения.

`approvalRequirement(action, policy)`:

| Риск     | По умолчанию                                                                                                                                                                     | Владелец может                                                                      |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| LOW      | без одобрения                                                                                                                                                                    | включить одобрение (`alwaysApprove`)                                                |
| MEDIUM   | внутри Ketner — без одобрения; наружу (сообщение клиенту, значимое изменение записи) — одобрение каждого раза, **если нет заранее выданного разрешения** (`standingPermissions`) | выдать постоянное разрешение или включить одобрение всегда                          |
| HIGH     | одобрение                                                                                                                                                                        | не может отключить (разрешение не действует)                                        |
| CRITICAL | запрещено                                                                                                                                                                        | только при проверенном процессе (`verifiedCriticalProcesses`), и тогда с одобрением |

«Одобрять всегда» сильнее постоянного разрешения. Решения владельца (08.11.2026): сообщение одному клиенту — MEDIUM при заранее выданном разрешении; изменение записей — по последствиям (обычное обратимое — LOW, значимое или необратимое — MEDIUM), а не всегда MEDIUM.

**Существующие агенты не меняют поведения.** `legacyApprovalPolicy('customer_bot')` выдаёт постоянное разрешение на `reply.send_in_session`: включая бота, владелец уже разрешил ему отвечать посетителям. Остальные действия существующих агентов — LOW. Тест проверяет, что ни одному существующему агенту не нужно новых одобрений.

## 4. AgentSpec

Поля: `name`, `role`, `objectives`, `instructions`, `tone`, `language`, `knowledge` (`inline`, `examples`, `corrections`, `documents`), `allowedActions` (id словаря), `restrictions`, `escalation`, `input`, `output`, `modelPolicy` (`selection: 'auto'`, `maxCreditsPerReply`), `memoryPolicy`, `limits` (шаги, вызовы действий, таймаут, суточный потолок), `channel` (`ketner_chat`, `public_page` со `slug`/`greeting`/`quickReplies`, `workflow`), `testing`.

**Рантайма в спецификации нет** (схема строгая — поле `runtime` отклоняется).

`checkAgentSpec`: неизвестные и запрещённые действия, повторы, согласованность лимитов, форма заявки только на публичной странице и только с `lead.create`.

| `AssistantConfig.knowledge / examples`                                                        | `knowledge.inline / knowledge.examples`                                                                                                            |
| `AssistantConfig.restrictions`                                                                | `restrictions`                                                                                                                                     |

`agentSpecToLegacy(agentSpecFromLegacy(x))` возвращает `x` в точности — проверено на шести наборах: обычный помощник, помощник с пустыми необязательными полями, помощник на пределах длины, бот, бот без кнопок, приветствия и исправлений с минимальным потолком, бот на всех пределах. Шаблон `study_assistant` — инструмент, а не агент: перевод для него не определён.

## 5. Привязка к рантайму

`RuntimeBinding = { bindingVersion, solutionId, agentVersion, runtime }`. Профили рантаймов:

| Рантайм         | Подключён  | Память                         | Каналы  |
| --------------- | ---------- | ------------------------------ | ------- |
| `agent_gateway` | да         | `none`, `conversation`         | все три |
| `mastra`        | нет (T4.0) | `none`, `conversation`, `task` | все три |

`bindRuntime(spec, target)` по умолчанию выбирает `agent_gateway` и отклоняет привязку с причинами, если рантайм не подключён или не поддерживает требования спецификации. Спецификация при этом не меняется.

## 6. SolutionSpec

Поля: `title`, `source`, `businessContext`, `problem`, `expectedOutcome`, `successCriteria`, `type` (`assistant/tool/workflow`, как в смете), `strategy` (`agent`, `tool`, `workflow`, `workflow_calls_agent`, `agent_calls_workflow`), `trigger`, `components` (`agents`, `workflows`, `tools`), `requires`, `integrations`, `knowledgeSources`, `input`, `output`, `permissions`, `failureHandling`, `testing`, `effort`, `estimateId`, `assumptions`, `unknowns`.

Процесс описан на языке Ketner: шаги — действия словаря с описанием и поведением при ошибке. Ещё два поля фиксируют факты о решении, а не правила исполнителя:

- `logicOrigin` — кто задал логику: `catalog_template` (шаблон каталога Ketner), `staff_built` (сотрудник под клиента), `generated` (сгенерировано или изменено ИИ под клиента);
- `instantiation` — `shared` (один процесс на всех) или `per_customer` (экземпляр на клиента).

Схема проверяет структуру: согласованность стратегии и состава, шаблон только у процессов из каталога, уникальность ключей. `checkSolutionSpec` проверяет словари: действия известны, действия шагов входят в `permissions`. **Ограничения n8n в схеме нет:** спецификация с `logicOrigin: 'generated'` валидна.

## 7. Совместимость и политика исполнения

`evaluateSolution(spec, ctx)` возвращает `{ status, issues, approvals }`. Статусы по убыванию: `blocked`, `needs_confirmation`, `needs_integration`, `needs_setup`, `ready`.

| Проверка            | Источник                                                                                                              |
| ------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Словари Ketner      | `checkSolutionSpec`                                                                                                   |
| Интеграции          | требования решения + требования его действий → реестр возможностей (`available / setup / integration / unavailable`)  |
| Поставщик процессов | выбран и развёрнут; поддерживает триггер и действия шагов                                                             |
| Лицензия            | `provider.license(workflow)` → `allowed`, `requires_confirmation` (ключ подтверждения), `requires_commercial_license` |
| Рантайм агентов     | шаблон компонента — агент; рантайм подключён                                                                          |
| Одобрения           | `approvalRequirement` для каждого действия; запрещённое — блокировка                                                  |

Профиль `N8N_COMMUNITY`:

- **Лицензия:** `generated` → `requires_commercial_license`; копия шаблона каталога на клиента → `requires_confirmation` (`n8n_per_customer_copy`); остальное → `allowed`.
- **Действия:** знания, черновик, заявка, уведомление (через API Ketner), изменение, удаление и сообщения. Денег и договоров нет.
- **Триггеры:** `webhook`, `schedule`, `manual`, `channel_event`.
- **Учётные данные:** `api_key`, `service_account`, `oauth_tokens_via_api` — раздел 2.4 [N8N_DEPLOYMENT.md](N8N_DEPLOYMENT.md).

Замена n8n — новый профиль; тест показывает, что та же спецификация с ИИ-логикой заблокирована на n8n CE и готова на исполнителе без такого ограничения.

## 8. Жизненные циклы — четыре отдельных автомата

| Автомат              | Состояния                                                                                            | Откуда сейчас                                                                                                                          |
| -------------------- | ---------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Решение              | `draft → approved → archived`                                                                        | `activeVersion === null` → `draft`, иначе `approved`; `archived` — удаление                                                            |
| Развёртывание агента | `not_deployed`, `testing`, `ready`, `active`, `paused`, `failed`                                     | `solutions.status` + последний прогон тестов: текущая версия, текущий отпечаток кейсов, все кейсы прошли (ручной вердикт важнее судьи) |
| Процесс              | `draft`, `validated`, `provisioned`, `active`, `inactive`, `failed`, `archived`                      | Данных пока нет (этап 6)                                                                                                               |
| Запуск процесса      | `queued`, `waiting_approval`, `running`, `succeeded`, `failed`, `retrying`, `cancelled`, `timed_out` | Данных пока нет; `canRetry` ограничивает число повторов                                                                                |

`legacyStatusOf` сводит развёртывание агента к колонке `solutions.status` (`draft/active/paused`), и тест проверяет согласованность в обе стороны. Состояние `failed` из текущих данных не выводится — оно появится вместе с журналом исполнений (T1.4).

## 10. Что не сделано и требует решения

Решено владельцем 08.11.2026: AgentSpec выводится из существующих данных; формат хранения пока не меняется; сообщение одному клиенту — MEDIUM при заранее выданном разрешении; изменение записей — по последствиям.

1. **Схемы черновиков для модели** (`agentDraftSchema`, `solutionDraftSchema`) и сборка `SolutionSpec` из `Opportunity` — вместе с генерацией (T7.1).
2. **Подключение к продукту:** ни один маршрут не использует модуль. Первое применение — показ состояния развёртывания и отчёта совместимости в Builder; требует отдельного разрешения (маршруты и сайт).
3. **Где хранить заранее выданные разрешения и привязку к рантайму** — вместе с журналом исполнений (T1.4), отдельной миграцией. До этого используется `legacyApprovalPolicy`.
4. **`record.delete` — CRITICAL** (необратимое удаление). Если понадобится обратимое удаление (корзина у провайдера), нужно отдельное действие с риском HIGH.
5. **OAuth через n8n** проверен опытом (создание с токенами, обновление по 401, хранение) — [N8N_DEPLOYMENT.md](N8N_DEPLOYMENT.md), раздел 2.4. Для каждого нового OAuth-провайдера нужно проверить, отвечает ли он 401 на просроченный токен.
