# Builder v1: мастер решения (проект, без кода)

Статус: проект на ревью, 23.11.2026. Кода в этом PR нет.

Основа — решения владельца от 23.11.2026:

- только подписка;
- Builder v1 — пошаговый мастер «Анализ → Настройка → Подключения → Запуск» с шаблонами автоматизаций
  и переключателями;
- схема процесса строится из настройки и только показывается;
- свободный редактор процессов — позже;
- экономия — оценка из цифр клиента с подписью «оценка», после запуска её заменяет реальная
  статистика.

**Макеты.** Владелец пришлёт четыре концепт-макета: гибридное решение, процесс, ИИ-агент, ИИ-помощник.
Это направление, а не попиксельное ТЗ. На момент этого черновика макетов ещё нет. Когда они придут,
сверяю разделы 2–7 и отмечаю расхождения в этом же PR, прежде чем делить работу (раздел 11).

Мастер не вводит новой модели данных для решения: он заполняет `SolutionSpec` (и `AgentSpec` для
агентов) по шагам. Исполняют то, что уже исполняет платформа. Новое — только каталог шаблонов
автоматизаций (раздел 4) и хранение их переключателей.

## 2. Типы решений и что за ними стоит сегодня

| Тип в мастере     | Что это для клиента                                                | `SolutionSpec.strategy`      | Что есть сегодня                                                                                     | Чего нет                                                      |
| ----------------- | ------------------------------------------------------------------ | ---------------------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| **ИИ-помощник**   | Разговор с владельцем или сотрудником: отвечает, пишет, считает    | `agent`, канал `ketner_chat` | Шаблон `personal_assistant`, `study_assistant` (инструмент); чат Ketner закрыт переключателем `chat` | Помощник в Telegram сотрудника — позже                        |
| **ИИ-агент**      | Говорит с клиентами бизнеса и действует: отвечает, собирает заявки | `agent`, канал `public_page` | Бот для клиентов: страница, виджет, QR; путь платформы (`bot-agent.ts`), эскалации, форма заявки     | Канал Telegram клиента (отдельный проект, PR после этого)     |
| **Автоматизация** | Процесс по событию или расписанию без разговора                    | `workflow`                   | Шаги «по событию заявки»: заявка → таблица, заявка → менеджер                                        | Расписание (`scheduled_runs` — unavailable), вебхуки, CRM     |
| **Гибрид**        | Агент + автоматизации вокруг него                                  | `agent_calls_workflow`       | Ровно то, что работает у бота сейчас: агент собирает заявку, автоматизации её разносят               | Процесс, который сам вызывает агента (`workflow_calls_agent`) |

В v1 «Автоматизация» без агента ограничена тем, что умеет движок: шагами по событиям Ketner (заявка),
а с расписанием — после `scheduled_runs` (раздел 4, «сводка за день»). Тип, для которого нет нужной
возможности, мастер показывает как «пока недоступно», с причиной из каталога возможностей. Молча
он не подменяется другим типом (как сейчас в шаблонах).

## 3. Четыре шага мастера и что каждый сохраняет

Каждый шаг сохраняет свой результат сразу. Вернуться можно к любому пройденному шагу. Решение
остаётся черновиком (`solutions.status = draft`), пока не нажат «Запустить» на шаге 4.

### Шаг 1. Анализ

- **Вход:** анализ бизнеса (как сейчас) или выбор шаблона решения из галереи.
- **Показывает:** возможность, тип решения (раздел 2), что сделает Ketner, что — команда, чего пока
  нет, оценку экономии (раздел 9).
- **Сохраняет:** черновик решения и `SolutionSpec` с `source = {analysisId, opportunityId}`,
  `type`, `strategy`, `trigger`, `requires`, `integrations`.

### Шаг 2. Настройка

- **Агент и помощник:** имя, задача, тон, знания (сайт, документы, текст), приветствие, частые
  вопросы. Это поля бота и помощника, которые уже есть, плюс то, что модель предлагает при создании
  черновика. Тест-кейсы видны и запускаются тут же.
- **Автоматизации:** каталог шаблонов с переключателями (раздел 4). Включённый шаблон добавляет шаг в
  `components.workflows[].steps` и действие в `permissions`.
- **Сохраняет:** версию настройки агента (`solution_versions`, как сейчас), переключатели
  автоматизаций (раздел 4.2), `SolutionSpec.components`.

### Шаг 3. Подключения

- **Карточки сервисов**, которые нужны включённым автоматизациям и каналам (раздел 6). Подключение
  делает сам клиент своим аккаунтом (`connectedBy: 'customer'`).
- **Сохраняет:** сами подключения, как сейчас (`google_connections` и будущие таблицы подключений).
  В решении — только ссылка «какой сервис нужен», без токенов.

### Шаг 4. Запуск

- Схема (раздел 5) и проба (раздел 7).
- **Перед запуском — проверка:**
  1. тесты агента прошли, как сейчас;
  2. все нужные подключения в состоянии `connected`;
  3. действия с риском `medium` и выше одобрены (`approvalRequirement`);
  4. есть активный тариф и в нём есть место (раздел 8).
- **Сохраняет:** включённую версию (`active_version`), `status = active`. С этого момента решение
  считается активным по тарифу.

### 4.1. Каталог (начало)

| Шаблон                    | Событие                 | Шаги (действия `risk.ts`)                                  | Риск                                        | Подключение                         | Статус                               |
| ------------------------- | ----------------------- | ---------------------------------------------------------- | ------------------------------------------- | ----------------------------------- | ------------------------------------ |
| **Заявка → таблица**      | новая заявка бота       | `sheet.append_row`                                         | low (внешняя запись одной обратимой строки) | Google Таблицы                      | работает (этап F)                    |

Каталог — код, как `builder/templates.ts`: id, версия, событие, шаги, действия, нужные

Дальше по очереди, после первых клиентов:

- заявка → amoCRM / Bitrix24 (`record.update`, medium — одобрение при включении);
- запись в календарь (`calendar`, отдельный проект);
- напоминание клиенту (канал клиента, high — массовая отправка только с одобрением).

### 4.2. Хранение переключателей

У бота переключатели уже лежат в его JSON (`bot.leadNotify`, подключение Таблицы — в
`google_connections`). Для v1 предлагаю общее поле решения `automations: { [templateId]: { enabled,
version, options } }`:

- для бота — в том же JSON `solutions.bot`, без миграции;
- для решений других типов — в `SolutionSpec` версии.

Включение шаблона:

1. проверяет его действия по `approvalRequirement`: `low` — включается сразу; `medium` с внешним
   охватом и выше — нужно «Подтверждаю» с текстом, что именно будет делаться;
2. добавляет шаг в `components.workflows` (`logicOrigin: 'catalog_template'`, `template: {id,
version}`);
3. показывает нужные подключения на шаге 3.

Выключение останавливает новые запуски. Уже начатые эффекты журнала доводятся или сверяются по
своим правилам.

## 5. Схема процесса: только для чтения

Схема строится из `SolutionSpec`, а не рисуется руками:

```
[Триггер] → [Агент: имя, канал] → [Событие: заявка]
                                        ├→ [Таблица: Заявки Ketner]  (состояние подключения)
                                        └→ [Менеджер: почта, Telegram]
```

- **Узлы:**
  - триггер (`trigger.kind`);
  - компоненты (`agents`, `workflows`, `tools`);
  - шаги включённых шаблонов (`workflows[].steps` по порядку);
  - конечные точки — подключения из `integrations`.
- **Связи:** триггер → агент (для `agent*`-стратегий); агент → событие (заявка, эскалация); событие →
  шаги шаблонов.
- **На узле:** название, иконка сервиса, уровень риска действия (бейдж `low/medium/high`),
  состояние подключения (раздел 6) и после запуска — счётчики за 7 дней (раздел 9).
- **Отрисовка:** детерминированная раскладка слева направо (уровни по глубине графа), SVG без
  библиотек; на телефоне — вертикальный список тех же узлов. Схема — `role="img"` с текстовым
  описанием, рядом — тот же список текстом (доступность).
- **Нельзя:** перетаскивать, добавлять узлы, соединять вручную. Это свободный редактор, вне v1.

Схема и описание строятся одной функцией `diagramFromSpec(spec, connections, stats)`, общей для
сервера и сайта. Тест: для каждого шаблона каталога — снимок узлов и связей.

## 7. Проба

- **Агент:** чат «как клиент» с текущей, ещё не включённой версией. Это уже есть
  (`/bot/preview`); платит бесплатный лимит создания (P2) и в обращения не считается.
- **Автоматизации:** «Проверить на тестовой заявке» создаёт заявку с пометкой «проба» и проводит её
  по включённым шагам с настоящими подключениями. Строка в таблице помечается «проба» в колонке
  «Бот», письмо и Telegram идут с пометкой «Проба». Владелец видит результат каждого шага (✓ / ✗ с
  причиной). Проба не считается обращением (`trigger_kind = manual`) и не создаёт заявку в списке.
- Шаги с риском `medium+` в пробе только показывают, что было бы сделано, без внешнего вызова,
  пока их не одобрили.

## 8. Тариф в мастере

Решение владельца: всё работает только при активном тарифе.

- **Шаги 1–3 и проба** работают без тарифа (бесплатный лимит создания, P2).
- **Шаг 4 «Запустить»** без тарифа: экран «Нужен тариф» с тарифами из каталога и тем, что войдёт в
  выбранный. Решение остаётся черновиком.
- **Место в тарифе** проверяется при запуске и при подключении, а не при ответе (как в
  SUBSCRIPTION_PRICING_DESIGN, раздел 3):
  - «Активных решений: 1 из 1 — тариф Start». Запустить второе нельзя, предлагается тариф выше или
    выключить первое;
  - «Внешних сервисов: 0 из 0 — тариф Start». Подключить Таблицу на Start нельзя, если подключения
    считаются (см. открытый вопрос ниже).
- **В шапке мастера** — строка тарифа: имя, решения X/Y, обращения за месяц, внешние сервисы X/Y.
- **Тариф закончился:** решения не удаляются, переходят в режим «только заявки» (как при 110%), на
  карточках — «Тариф не активен». Автоматизации по заявкам продолжают уведомлять владельца: заявка
  не должна теряться.

**Открытые вопросы владельцу:**

1. **Каналы.** Считать ли каналы (сайт, Telegram клиента) «внешними сервисами»? Рекомендация
   ревьюера: нет, считать только системы данных (Таблицы, CRM, Календарь). Так страница бота,
   виджет и Telegram клиента не съедают «сервисы» тарифа. Это расходится с таблицей 2.1 в
   SUBSCRIPTION_PRICING_DESIGN, где Telegram-бот клиента — внешний сервис; при решении «нет»
   таблицу нужно обновить.
2. **Таблица на Start.** У Start 0 внешних сервисов, а Google Таблицы открыты всем (шаг 5b). Сейчас
   лимит сервисов в коде не проверяется (`activeSolutions` и `externalServices` есть только в
   каталоге). Нужно решить: Таблица на Start разрешена, Start даёт 1 сервис, или подключение
   блокируется до тарифа Growth. До решения ничего не меняю. На сайте `EXTERNAL_SERVICES_LIVE =
false` («появятся позже») — после решения включить.
3. **Возможность в каталоге анализа.** `spreadsheets_sync` в каталоге возможностей анализа — по-прежнему
   `unavailable`, хотя «заявка → таблица» работает. Предлагаю `partial`: «строки заявок — да,
   синхронизация произвольных таблиц — нет». Это отдельный маленький PR.

## 9. Оценка экономии

Источник — уже работающий `discovery/impact.ts`. Число появляется, только если клиент сам назвал,
сколько раз и сколько минут занимает задача (с цитатой из его текста). Мастер это не меняет, а
показывает так:

- **Формула** (как в анализе): `часы в неделю = раз в неделю × минут на раз / 60 × доля ИИ`. Доля ИИ
  — диапазон-допущение по типу задачи: `low` 10–30%, `medium` 30–60%, `high` 60–80%. Итог — «от–до».
- **Деньги** — только если клиент назвал стоимость часа: `₸/$ в месяц = часы в неделю × 4,33 ×
стоимость часа`. Без стоимости часа — только часы.
- **Подпись всегда:** «Оценка по вашим цифрам: N раз в неделю × M минут. Доля, которую возьмёт ИИ, —
  допущение X–Y%. Реальные цифры появятся после запуска». Рядом — «как посчитано» с формулой и
  вводными. Без цифр клиента — только качественная польза и вопрос, каких данных не хватает.
- **После запуска** оценку заменяет статистика за 7 и 30 дней:
  - обращений (по правилу счётчика тарифа);
  - заявок;
  - передано человеку;
  - доля разговоров, закончившихся без человека;
  - записано в таблицу / не записано;
  - уведомлений отправлено.

  Экономия по факту: `обращений без человека × минут на раз (из анализа) / 60`, с подписью
  «по фактическим обращениям и вашей оценке времени на одно». Оценка из анализа остаётся в
  «как было до запуска», мелким шрифтом.

- **Нельзя:** проценты конверсии и выручки без данных клиента («+40% конверсии»), отраслевые
  средние без источника, «окупится за N дней» без цены и данных клиента. Тест текстов мастера
  проверяет, что таких формулировок нет.

## 10. Что сознательно не входит в v1

- Свободный редактор процессов: узлы, связи, условия, ветвления, циклы.
- Произвольные вебхуки и HTTP-шаги, код в шагах.
- Расписание и «сводка за день», пока нет планировщика (`scheduled_runs`). Шаблон виден как «скоро».
- CRM (amoCRM, Bitrix24) и Календарь — после первых клиентов, отдельными проектами.
- Канал Telegram клиента — свой проект (`docs/TELEGRAM_CHANNEL.md`), в мастере появляется карточкой
  после него.
- Массовые рассылки клиентам (риск `high`).
- Несколько агентов в одном решении, процесс, вызывающий агента (`workflow_calls_agent`).
