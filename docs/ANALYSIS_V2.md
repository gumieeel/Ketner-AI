## 0. Зачем

Владелец прогнал анализ на своём бизнесе («сфера услуг, внедрение ИИ в бизнес») и получил личного
помощника для черновиков, инструмент сводок и бота для клиентов. Это слабо и не продаёт. Причины
в коде (разбор 26.11.2026):

| --- | --------------------------------------------------------------------------------------------------------------- | --------------------------- | -------------------------------------------------------------- |
| 1   | Бесплатный режим — `ketner-mini` (GPT-6 Luna) с effort `low` на всех этапах                                     | `discovery/model-policy.ts` | раздел 5                                                       |
| 2   | Промпты замыкают поиск на сегодняшнем каталоге: три рецепта, «не обещай того, чего нет», «сначала самое лёгкое» | `discovery/prompts.ts`      | разделы 2–3                                                    |

| 6   | У модели нет знаний об отрасли                                                                                  | —                           | раздел 2                                                       |

Решения владельца, на которых стоит этот документ:

- Поиск возможностей — `claude-sonnet-5.5`, effort `medium`. Разбор описания и план остаются на
  дешёвой модели. Ожидаемая цена — около $0.15–0.30 за анализ. Полный анализ резервируется в
  суточном бюджете до старта; бюджет кончился — честное «лимит на сегодня исчерпан».
- Ценные автоматизации, которых Ketner пока не умеет (CRM, запись в календарь, повторные касания,
  мессенджеры), показываются честно, как «скоро», с кнопкой «Хочу это». Это лист ожидания по
  возможности, с подсчётом в админке. Доступными они не выдаются никогда.
- Анализ всегда бесплатный и одного вида: платного и «глубокого» режимов больше нет. Тариф даёт
  больше анализов в сутки и полный план; без тарифа — краткий план (раздел 5.5).
- Разовых смет «под ключ» и кнопки «Запросить предложение» в анализе нет: работает только
  подписка. Работа с командой — часть платного тарифа (раздел 3.3).

## 1. Чтение сайта

### 1.1 Какие страницы

До **10 страниц** одного сайта: главная и до 9 внутренних.

1. **Главная** — как сейчас.
2. **Список страниц.** `robots.txt` → строки `Sitemap:`; иначе `/sitemap.xml`. Индекс карт
   раскрывается на один уровень; разбирается не больше 500 адресов и 300 КБ XML.
3. **Без карты сайта** — ссылки из `<nav>`, `<header>` и `<footer>` главной.
4. **Отбор.** Адреса оцениваются по словам в пути и тексте ссылки, по группам:

   | Группа            | Слова (ru / kk / en)                                     |
   | ----------------- | -------------------------------------------------------- |
   | услуги            | услуги, services, прайс, цены, price, стоимость, каталог |
   | о компании        | о нас, о компании, about, команда                        |
   | контакты          | контакты, contacts, адрес, как добраться                 |
   | вопросы           | faq, вопросы, помощь                                     |
   | запись и доставка | запись, booking, онлайн-запись, доставка, оплата         |

   Берётся до двух страниц на группу, по порядку групп. Свободные места — по порядку в навигации.

5. **Что пропускается:**
   - другой хост: разрешены только тот же хост и его вариант с `www.`; поддомены — нет;
   - адреса, отличающиеся только параметрами запроса или якорем;
   - файлы: `.pdf`, картинки, архивы;
   - страницы входа и корзины;
   - `Disallow` из `robots.txt` для `User-agent: *`.

### 1.2 Безопасность и лимиты

Всё, что умеет `readSite` сейчас, применяется к **каждому** запросу: к `robots.txt`, карте сайта
и каждой странице.

- **Схема и порт:** только `http(s)`, порты 80 и 443.
- **Проверка адреса:** при каждом соединении, в `lookup` сокета.
- **Запрещённые адреса:** внутренние, служебные и зарезервированные (`isBlockedAddress`).
- **Переадресации:** до 3 на запрос, каждая проверяется заново. Переадресация на другой хост — страница
  пропускается.
- **Одна страница:** 8 с и 1,5 МБ.

Новые общие лимиты:

| Лимит                     | Значение                           |
| ------------------------- | ---------------------------------- |
| Страниц                   | 10                                 |
| Одновременных запросов    | 3                                  |
| Общее время чтения        | 20 с (что не успело — не читается) |
| Всего байт                | 6 МБ                               |
| Текста со страницы модели | 4 000 символов                     |
| Текста сайта модели всего | 16 000 символов                    |

Заголовок `User-Agent`: `KetnerBot/1.0 (+https://ketner.org/bot)`. Личных данных в запросах нет.

Страница `/bot` (новая, статическая, в PR B1) коротко объясняет владельцу сайта, кто читает его
страницы:

- зачем: человек попросил разобрать свой сайт;
- сколько: до 10 страниц за раз, только по такому запросу, без обхода по расписанию;
- что соблюдается: `Disallow` для `User-agent: *` в `robots.txt`;
- что хранится: факты и короткий текст — вместе с анализом, удаляются вместе с ним;
- ссылки на `/privacy` и на контакты.

### 1.3 Факты с доказательствами

Сервер разбирает **HTML**, не только видимый текст, и до вызова модели собирает факты. Каждый
факт: `{ kind, value, page, evidence }`, где `page` — путь страницы, `evidence` — цитата или
атрибут, до 160 символов.

| `kind`               | Как находится                                                                                               |
| -------------------- | ----------------------------------------------------------------------------------------------------------- |
| `channel`            | ссылки `wa.me`, `api.whatsapp.com`, `t.me`, `instagram.com`, `vk.com`, `tel:`, `mailto:`                    |
| `form`               | `<form>` с полями телефона, имени или почты; текст кнопки отправки                                          |
| `cta`                | кнопки и ссылки «Записаться», «Оставить заявку», «Купить», «Заказать звонок»                                |
| `booking_widget`     | `src` скриптов и `iframe` по таблице сигнатур: YCLIENTS, DIKIDI, Altegio, Calendly, формы Битрикс24 и т. п. |
| `crm_or_chat_widget` | таблица сигнатур: Битрикс24, amoCRM, JivoSite, Talk-Me, Wazzup, Envybox, Tawk.to и т. п.                    |
| `price`              | строки с валютой (₸, тг, тенге, ₽, руб., $, €) рядом с числом; до 20 штук                                   |
| `hours`              | `openingHours` в JSON-LD, «пн–пт 9:00–18:00», «круглосуточно»                                               |
| `business`           | JSON-LD `LocalBusiness`/`Organization`: название, телефон, адрес, `priceRange`                              |

Таблица сигнатур — в коде, с тестами на сохранённых фрагментах HTML. Неизвестный виджет фактом
не считается.

### 1.4 «Разбор сайта»

Новый раздел отчёта: что сейчас теряет заявки. Каждая строка — со ссылкой на страницу.

- **Правила сервера**, без модели, только по фактам:
  - форма есть, а канала мгновенного ответа нет («заявки с формы ждут ответа вручную», страница формы);
  - для отраслей с записью нет виджета записи («записаться можно только по телефону»);
  - нет ни одной цены («цены не указаны — клиент уйдёт спрашивать или к конкурентам»);
  - контакт только телефоном, без мессенджеров;
  - нет часов работы.
- **Находки модели** (`siteFindings` в выходе поиска возможностей): `{ issue, page, evidence }`.
  Сервер проверяет, что `evidence` действительно есть в тексте этой страницы, — так же, как
  сейчас проверяются числа (`verifyTaskNumbers`). Непроверенная находка отбрасывается.

Человек видит «Прочитали N страниц» со списком путей, затем до 6 пунктов разбора.

### 1.5 Хранение

Факты и короткий текст страниц хранятся в `analysis.source` (JSONB анализа). Всего до 40 КБ на
анализ. Удаляются вместе с анализом; отдельной таблицы нет.

## 2. Отраслевые плейбуки

### 2.1 Что это

Файл на отрасль: `apps/mock-api/src/discovery/playbooks/<industry>.ts`. Его пишут и проверяют
люди, в PR; модель его не генерирует. Поиск возможностей получает плейбук своей отрасли как
справочный материал. Модель подгоняет его под человека и может выйти за его пределы.

Отрасль — из `context.profile.industry`. Нет отрасли или `other` — общий плейбук малого бизнеса.

### 2.2 Формат пункта

```ts
interface PlaybookItem {
  id: string; // 'clinic_booking'
  title: Text; // «Онлайн-запись без администратора»
  pain: Text; // что болит, словами владельца
  trigger: Text; // «Пациент пишет в WhatsApp или на сайте»
  steps: Text[]; // 2–6 шагов агента
  result: Text; // «Запись в расписании, напоминание за день»
  dataNeeded: Text[]; // «расписание врачей», «прайс»
  capabilities: CapabilityId[]; // из каталога; статус считается при запросе, не пишется в файл
  signals?: SiteSignal[]; // какие факты сайта делают пункт уместным ('no_booking_widget')
}
```

Правила:

- **Без чисел-бенчмарков.** В плейбуках нет «+30% записей» и «экономит 10 часов». Тест проверяет,
  что в текстах нет чисел с `%`, «часов», «раз» и т. п. Числа в отчёте — только из данных человека,
  как сейчас.
- **Статус не хранится в плейбуке.** «Запускается сейчас» или «скоро» считается по каталогу в
  момент анализа (раздел 3.3). Когда Ketner научится новому, плейбук не меняется.
- **Объём в промпте:** до 4 000 символов на плейбук.

## 3. Выход поиска возможностей

### 3.1 Две группы

- **«Главное, что стоит автоматизировать»** — 1–3 возможности по ценности для этого бизнеса. Могут
  быть «скоро». Ранжирует модель (`valueRank` и одна фраза «почему это главное»), по потерям из
  разбора сайта и ответов.
- **«Можно запустить сегодня»** — всё, что Ketner умеет сейчас, по ценности. Если главная
  возможность запускается сейчас, она стоит в первой группе и во второй не повторяется.
- Остальное — под «Показать ещё».

### 3.2 Поля возможности (новые — жирным)

| Поле                           | Что это                                                                                                                                                                                                                                                                                                                                                                                           |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| title, problem, solution       | как сейчас                                                                                                                                                                                                                                                                                                                                                                                        |
| **lostNow**                    | что теряется сейчас: `{ text, source: 'site' \| 'answer' \| 'description', page?, evidence? }`; `evidence` проверяется сервером, как находки сайта                                                                                                                                                                                                                                                |
| **flow**                       | `{ trigger, steps[], result }`: что делает агент по шагам. Словарь совпадает с автоматизациями конструктора: события `lead.created`, `message.received`, `schedule.daily`, `form.submitted`, `booking.created`; действия `reply.send_in_session`, `lead.create`, `owner.notify`, `sheet.append_row` и действия «скоро»: `crm.create_deal`, `calendar.book`, `message.followup`, `messenger.reply` |
| **connect**                    | что подключить: `[{ capability, label }]`; статус каждого — сервер                                                                                                                                                                                                                                                                                                                                |
| requires                       | как сейчас: из него сервер считает статус                                                                                                                                                                                                                                                                                                                                                         |
| impact                         | как сейчас: часы — только из чисел человека, с подписью «оценка»                                                                                                                                                                                                                                                                                                                                  |
| **valueRank**, **valueReason** | место по ценности и одна фраза почему                                                                                                                                                                                                                                                                                                                                                             |
| **status**                     | считает сервер, не модель (3.3)                                                                                                                                                                                                                                                                                                                                                                   |

Правило промпта: **рабочий процесс важнее чат-бота**, когда у задачи есть событие бизнеса (заявка,
запись, заказ). Бот для клиентов остаётся одной из возможностей, а не ответом на всё.

### 3.3 Статус

Считает сервер по `requires` и каталогу:

| status | Когда                                                                            | Метка                |
| ------ | -------------------------------------------------------------------------------- | -------------------- |
| `now`  | есть готовая автоматизация (рецепт), и все требования доступны или настраиваются | «Запускается сейчас» |
| `soon` | нужна возможность из списка ожидания (4.2)                                       | «Скоро» + «Хочу это» |
| `team` | нужна работа команды (правила `pricing/delivery.ts`: вид поставки `team`)        | «С командой Ketner»  |

- `soon` никогда не получает кнопку запуска. Проверка — в тесте отчёта, как в PR A.
- `team`: помощь команды — часть платного тарифа.
  - **Кнопка** «Обсудить с командой»: форма связи или ссылка на Telegram поддержки. Без цены.
  - **Без активного тарифа** вместо кнопки — «Доступно на платном тарифе» и ссылка на `/pricing`.
  - **Из отчёта убираются** блок сметы (диапазон цены, строки работ, «Если внедрять вместе») и
    кнопка «Запросить предложение» — у всех возможностей, не только у `team`.

**Что остаётся от смет и почему.** Строки работ (`workItems`) и расчёт `pricing/` остаются на
сервере: только по ним `pricing/delivery.ts` решает, сделает ли человек это сам или нужна команда.
Без них статус `team` считать нечем. В ответ отчёта цены больше не попадают: сервер отдаёт только
статус. Админка заявок (`/admin/requests`) остаётся для уже поданных заявок; новые из анализа не
создаются. Убрать расчёт цен целиком можно отдельным PR, когда правила «сам или команда»
переедут на `requires` и каталог; в этот план это не входит.

### 3.4 Связь с конструктором

`flow.trigger` и `flow.steps` пишутся в словаре автоматизаций (`builder/automations.ts`). Тогда
«Запустить» у возможности со статусом `now` открывает мастер с уже включёнными шаблонами. Пример:
«заявка → менеджер» и «заявка → таблица» включены, если они есть в шагах.

## 4. Лист ожидания «Хочу это»

### 4.1 Данные

Запись: `{ capability, userId, analysisId, opportunityId, createdAt }`. Одна запись на пару
(аккаунт, возможность); повторное нажатие ничего не добавляет.

**Где хранить** — `ketner_docs` (решение 5), пространство `waitlist`, `id = <capability>:<userId>`:

- миграция не нужна (`migration-list.ts` не трогается);
- так уже хранятся отметки уведомлений и предпочтения;
- подсчёт — один SQL по JSONB, при таком объёме этого хватает.

Своя таблица понадобится, только если нужны будут отчёты сложнее подсчёта; это отдельная
миграция и отдельное решение владельца.

Удаление аккаунта стирает его записи: пространство добавляется в `account-erasure-setup.ts`.

### 4.2 Какие возможности

`WAITLIST_CAPABILITIES` — явный список в коде:

| id                 | Что это                                                          | Есть в каталоге                                                             |
| ------------------ | ---------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `crm`              | CRM (amoCRM, Битрикс24)                                          | да                                                                          |
| `calendar_booking` | запись в календарь или расписание                                | **нет — новое id**                                                          |
| `follow_ups`       | повторные касания клиента по расписанию                          | **нет — новое id** (сейчас ближе всего `scheduled_runs`)                    |
| `messengers`       | ответы в WhatsApp, Instagram, Telegram клиента                   | да                                                                          |
| `email`            | работа с почтой                                                  | да                                                                          |
| `auto_posting`     | посты по расписанию в Telegram-канал владельца (позже Instagram) | **нет — новое id**; агент для контента — [roadmap.md](roadmap.md), пункт 38 |

Других «скоро» не бывает: возможность вне списка и без готовой автоматизации идёт в «остальное» с
честным текстом, без кнопки.

### 4.3 Интерфейс и API

- **Кнопка у «скоро»:** «Хочу это». После нажатия — «Вы в списке» и строка «Учтём, когда будем
  решать, что делать дальше».
  - **Никаких обещаний** письма или срока.
  - **Гость** — сначала вход, с возвратом к отчёту: нужен аккаунт.
- **API:**
  - `POST /api/waitlist` `{ capability, analysisId?, opportunityId? }`;
  - `DELETE /api/waitlist/:capability`;
  - в ответе отчёта — флаг `wanted` у каждой «скоро».
- **Админка, раздел «Спрос»:** по каждой возможности — всего, за 30 дней, за 7 дней, и последние
  50 записей (почта аккаунта, отрасль из анализа, дата). Видят только администраторы.

## 5. Модель, цена, бюджет, сбои

### 5.1 Модели по этапам

Режим анализа один (решение 2): `paid` и `deep` убираются из интерфейса и из `model-policy.ts`.

| Этап               | Модель                          |
| ------------------ | ------------------------------- |
| Разбор описания    | GPT-6 Luna, effort `low`        |
| Поиск возможностей | **Claude Sonnet 5.5, `medium`** |

Старые анализы с `mode: 'paid'` или `'deep'` остаются читаемыми: поле хранится, новые с ним не
создаются. Экран выбора режима и цена «за кредиты» с главной и со страницы анализа уходят.

### 5.2 Цена (по `stagePolicy`, цены реестра на 27.11.2026)

Сейчас:

| Этап                                                 | Модель     | Потолок со вторым вызовом | Типично |

| Разбор                                               | GPT-6 Luna | $0.0043                   | $0.0015 |
| Поиск                                                | GPT-6 Luna | $0.0079                   | $0.0031 |
| Краткий план                                         | GPT-6 Luna | $0.0037                   | $0.0016 |

После перехода вход поиска растёт:

| Добавка к промпту                   | Символов                        | Токенов (худший случай, 2,2 символа на токен) | $ на попытку |
| ----------------------------------- | ------------------------------- | --------------------------------------------- | ------------ |
| Сайт, вместо 6 000 символов главной | до 16 000                       | +4 550                                        | +$0.0096     |

Итог бесплатного анализа:

- **потолок** ≈ $0.0043 + ($0.2526 + 2 × $0.0134) + $0.0037 ≈ **$0.29** — верх диапазона владельца;
- **типично** ≈ **$0.07–0.10**: Sonnet обычно пишет 4–6 тыс. токенов, а не 9,5.

Точные числа даст прогон набора оценки (раздел 6); после него поправим `TYPICAL_TOKENS`.

### 5.3 Резерв бюджета

- **Как сейчас.** При создании бесплатного анализа резервируются потолки всех трёх этапов
  (`freeReservationCaps`). После каждого этапа резерв закрывается фактической ценой; разница
  возвращается в суточный бюджет.
- **Изменение.** Резерв поиска — потолок Sonnet, около $0.28. Полный анализ целиком резервируется
  до старта; неполный не начинается.
- **Суточный бюджет.** Умолчание в коде меняется на $3 (`DISCOVERY_FREE_DAILY_USD`, сейчас 5);
  переменная окружения остаётся и перекрывает умолчание.
- **Что даёт $3:**
  - одновременно зарезервировано около 10 анализов;
  - за сутки, после возврата разницы, — порядка 30–40 анализов при типичной цене;
  - лимиты остаются (`PLATFORM_LIMITS.analyses`): 1 бесплатный в сутки на аккаунт или гостя, 5 с
    одного IP, 20 любых в сутки на владельца.
- **Бюджет кончился** до старта или на шаге «продолжить» после вопросов — человек видит:
  - без тарифа: «Бесплатные анализы на сегодня закончились. Приходите завтра»;
  - с тарифом анализы не зависят от общего бюджета (5.5), этот текст их не касается;
  - без технических слов и без ошибки.

### 5.4 Сбои

- **Ответ Sonnet не прошёл схему** — второй вызов, как сейчас (`STAGE_ATTEMPTS = 2`).
- **Провайдер недоступен или таймаут** — этап «не удался» с текстом «Не получилось завершить
  анализ. Повторите — это бесплатно» и кнопкой повтора. Повтор берёт новый резерв (так уже
  устроено).
- **Тихой подмены на дешёвую модель нет.** Шлюз вызывается со `strictModel`; это остаётся и
  закрепляется тестом: поиск возможностей не вызывается другой моделью ни при какой ошибке.
- **Время.** Sonnet с effort `medium` отвечает 40–90 с. Экран ожидания показывает шаги («Читаем
  сайт», «Подбираем решения для вашей отрасли»), а не таймер.

### 5.5 Анализы по тарифам

Предлагаю (числа — на одобрение владельца):

| Тариф          | Анализов в сутки | План    |
| -------------- | ---------------- | ------- |
| Без тарифа     | 1                | краткий |
| Старт ($10)    | 3                | полный  |
| Рост ($29)     | 5                | полный  |
| Бизнес ($89)   | 10               | полный  |
| Масштаб ($235) | 20               | полный  |

- **Кто платит.** Анализы с тарифом не берутся из общего бесплатного бюджета: их оплачивает
  тариф. Потолок одного анализа ≈ $0.29, типично ≈ $0.08. На «Старте» три анализа каждый день —
  до ≈ $26 в месяц в худшем случае и ≈ $7 типично, при цене тарифа $10. Поэтому поверх суточного
  числа — месячный предохранитель по себестоимости: не больше 50% цены тарифа (существующий
  механизм `billing/build-allowance.ts`, по которому сейчас идут платные этапы). Дошли до него —
  «На этот месяц анализы по тарифу закончились», без списаний.
- **Полный план** — тот же этап плана (GPT-6 Luna), но с полным числом шагов
  (`PLAN_STEPS.full`). Краткий — как сейчас бесплатный.
- Лимиты `PLATFORM_LIMITS.analyses` (по IP, запусков в минуту, 20 в сутки на владельца)
  остаются верхней границей для всех.

### 6.2 Прогон

- **Скрипт.** Расширение `scripts/benchmark-discovery.ts`: `--set eval --compare old,new`.
- **Конфигурации:**
  - «старая» — как на `main`;
  - «новая» — Sonnet, сайт, плейбуки, выход v2.
- **Результат** — Markdown «рядом», по случаям:
  - найденные и пропущенные «должно быть»;

- **Проверка «должно быть»** — по группам синонимов в коде. Итог всё равно смотрит человек: в PR
  кладутся отчёт целиком и полный ответ по случаю владельца.
- **Ключ.** Владелец заводит отдельный ключ OpenRouter с лимитом $5 и кладёт его в настройки среды

- **Предохранитель расходов.** Перед каждым вызовом скрипт складывает уже потраченное и потолок

  Сравнение готово — сообщаю владельцу, он удаляет ключ.
- Модели переключаются (PR B7) только после этого сравнения.

## 7. Текст для покупателя

Отчёт говорит словами владельца бизнеса. Внутренние слова в отчёт не попадают.

| Внутри                                            | В отчёте                                                   |
| ------------------------------------------------- | ---------------------------------------------------------- |
| возможность (opportunity)                         | «что можно автоматизировать»                               |
| рецепт, шаблон                                    | — (не показывается)                                        |
| выполнимость, статус реализуемости, `feasibility` | «Запускается сейчас» / «Скоро» / «С командой Ketner»       |
| смета, «под ключ», коммерческое предложение       | — (не показывается; у `team` — «Обсудить с командой»)      |
| требования, capability, каталог                   | «что подключить»                                           |
| `impact`, экономия                                | «оценка по вашим цифрам: ≈ N ч в неделю»                   |
| модель, промпт, кредиты                           | не упоминаются в отчёте (модель — в «Подробнее о расчёте») |

Разделы отчёта: «Что мы увидели на вашем сайте» → «Главное, что стоит автоматизировать» →
«Можно запустить сегодня» → «Что ещё можно сделать» → «Что проверил анализ».

Тексты статуса `team`:

- метка — «С командой Ketner»;
- строка под ней — «Это настроит команда Ketner вместе с вами. Помощь команды входит в платный
  тариф»;
- кнопка — «Обсудить с командой»; без тарифа — «Доступно на платном тарифе» и ссылка «Тарифы».

Тест `product-texts.test.tsx` проверяет, что в ключах `analysis.*` нет слов: рецепт, выполнимость,
реализуемость, capability, каталог, смета, «под ключ», «коммерческое предложение».

## 8. Что не меняется

- **Числа.** Проверка чисел по цитатам; часы — только из чисел человека.
- **Вопросы.** Обязательные вопросы о четырёх фактах (PR A).
- **Гостевой сценарий и лимиты** на человека и IP.
- **Строки работ и правила «сам или команда»** остаются на сервере (раздел 3.3) — для статуса
  `team`, не для цены.
