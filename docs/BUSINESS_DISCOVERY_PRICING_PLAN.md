## 2. Модули

```
discovery/ (было)            pricing/ (новое)
  schemas.ts  ── workItems ──▶ engine.ts      часы, деньги, сроки, уверенность (чистые функции)
  profile.ts  ── сигналы ────▶ usage.ts       подписка, поддержка, прогноз расхода ИИ
  service.ts  ── каталог ◀──── catalog.ts     каталог работ и настройки по умолчанию, zod-схемы
                               money.ts       целочисленная арифметика (BigInt)
                               service.ts     поколения смет, заявки, правки администратора, журнал
                               calibration.ts точность по фактическим проектам
                               store.ts       память и Postgres (миграция 0012)
                               views.ts       что видит клиент
routes/analyses.ts  (+ estimates, PATCH profile, POST requests)
routes/requests.ts  (мои заявки)
routes/pricing-admin.ts (админка, общий requireAdmin из routes/admin.ts)
```

Разделение ответственности (раздел 7 ТЗ):

- **модель**: что за бизнес, процессы, возможности, вид решения, какие работы нужны (id из каталога), ярлык сложности с причиной, неизвестные и допущения;
- **код**: проверка всего ответа схемой, проверка работ по каталогу, приведение сложности в допустимый диапазон, часы, деньги, резерв, минимум, округление, сроки, уверенность, права, журнал, учёт расхода.

## 3. Методика расчёта

Все числа — из действующей версии настроек и каталога (`pricing_versions`). Единицы: часы — центичасы, деньги — целые тенге, проценты — базисные пункты, коэффициенты — тысячные; умножение-деление через BigInt с округлением половины вверх (`pricing/money.ts`). Плавающая точка в суммах не используется.

1. **Проверка работ.** Для каждой работы из ответа модели: id есть в каталоге и это не служебная работа → иначе «нестандартная работа» (в цену не входит, нужна проверка). Статус `planned`/`disabled` → «пока не делаем» (в цену не входит, нужна проверка). Количество ограничено `maxQuantity`. Сложность модели приводится в `complexityRange` работы; не названа — `defaultComplexity`.
2. **Общие работы считаются один раз.** Одинаковые работы разных возможностей в общей смете сливаются: берутся наибольшие количество и сложность.
3. **Часы работы:** `часы = часы_каталога × количество × множитель_сложности` отдельно для мин/ожид/макс. Множители по умолчанию: просто 1.0, средне 1.5, сложно 2.2.
4. **Работы проекта** (`category: shared` — подготовка и архитектура; запуск, документация, передача) — один раз на смету, только если есть хоть одна работа в цене.
5. **Тестирование** — `testingPercent` от часов работ (не проекта).
6. **Неопределённость** расширяет **только максимум**: `+uncertaintyPercentPerUnknown` за каждую неизвестную, работу с ручной проверкой и неизвестный объём обращений (если есть ИИ-обработка), не больше `uncertaintyMaxPercent`. Ожидаемая оценка не расширяется — иначе риск считался бы дважды вместе с резервом.
7. **Деньги:** `работа = часы × billableHourlyRateKzt`. Ставка — **полная** (fully loaded): уже включает зарплату, налоги, накладные и маржу; отдельной наценки нет, маржа не применяется дважды, внутренняя себестоимость в системе не хранится.
8. **Прямые расходы** — `directSetupCostKzt × количество`, без множителя сложности; `null` — «неизвестно», в сумму не входит, клиенту показывается «по тарифам провайдера».
9. **Резерв на риски** — `riskReservePercent` от (работа + прямые) для ожидаемой и максимальной; у минимума резерва нет (оптимистичный, но реальный объём).
10. **Итог:** `max(сумма, minimumImplementationPriceKzt)`, округление **вверх** до `roundingIncrementKzt`; гарантируется мин ≤ ожид ≤ макс. Нет ни одной работы в цене — цены нет: «Требуется техническая проверка».
11. **Сроки** (рабочие дни, не часы): `⌈часы / workingHoursPerDay⌉ + дни на ответы клиента + наибольшее внешнее ожидание работ` (например, проверка Meta для WhatsApp 3–10 дней) — отдельно для мин и макс.
12. **Уверенность.** Низкая: нет работ в цене, есть исключённые или выведенные (не от модели) работы, 3+ неизвестных. Средняя: работа с ручной проверкой, есть неизвестные, неизвестен объём или неполный профиль. Иначе высокая. `technicalVerificationRequired` — есть исключённые/ручные/выведенные работы; заявка по такой смете сразу получает статус «Техническая проверка».
13. **Общая смета** — по возможностям, у которых есть цена (если их 2+); `sharedSavingsKzt` = сумма ожидаемых отдельных − ожидаемая общая. Покупать всё вместе не обязательно — это сказано клиенту.

Пример (тест `pricing/engine.test.ts`): Google Таблицы (простая) 2/4/6 ч + подготовка 2/3/5 + запуск 2/3/6 = 6/10/17 ч; при ставке 10 000 ₸, резерве 10%, без тестирования и минимальной цены → 60 000 / 110 000 / 187 000 ₸.

## 4. Расходы — три отдельные категории

1. **Разовое внедрение** — смета выше.
2. **Ежемесячно** — подписка «Автоматизации» (действующая цена $15/мес из `billing/automation-subscription.ts`, включает 7 500 кредитов; в тенге — только если администратор задал курс), поддержка — только если задана её цена.
3. **Переменные расходы** — прогноз расхода ИИ: обращений в месяц (из профиля, со слов человека) × вызовов × токенов × цена модели из реестра шлюза (+ комиссия пополнения OpenRouter). Без числа обращений — «зависит от числа обращений», без выдуманной суммы. Плата провайдерам (WhatsApp, Meta) — «по тарифам провайдера», не выдумывается. Это прогноз, не счёт; фактический расход списывается шлюзом кредитами, как и раньше. Кредиты агрегатора со сметой внедрения не смешиваются.

## 5. Данные (миграция `0012_implementation_pricing`, только добавление)

| Таблица                    | Что                                                                                                                                                                                                                                                                                                                                                                           |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pricing_versions`         | `version` (PK), `config`, `catalog`, `note`, `created_by`. Неизменяемы; новая версия = последняя + 1 (одновременная правка → 409). Первая создаётся из значений по умолчанию при первом обращении                                                                                                                                                                             |
| `implementation_estimates` | Сметы анализа поколениями: `analysis_id`, `generation`, `scope_key` (`opp:<id>`/`combined`, уникально в поколении), `pricing_version`, `fingerprint` входных данных, `data` (полный расчёт + прогноз). Новое поколение — только если изменились возможности, работы или профиль; смена цен существующие сметы не меняет. Стираются при удалении анализа и истечении гостевого |
| `implementation_requests`  | Заявка: `user_id`, `estimate_id`, `status`, `pricing_version`, `data` (снимок сметы, контакт, текст, проверенная смета, заметки, назначение, факт), идемпотентность `(user_id, idempotency_key)`, версия записи                                                                                                                                                               |
| `pricing_audit_log`        | Кто (`actor_id`), что (`action`), было (`previous`), стало (`next`), почему (`reason`), когда — для версий цен, смет и заявок                                                                                                                                                                                                                                                 |

На всех новых таблицах включён RLS без политик (защита от прямого доступа через API Supabase). Профиль бизнеса — в `discovery_analyses.context.profile` (без новой колонки): стирается вместе с анализом.

## 6. Заявки и предложение

Статусы: `new`, `reviewing`, `clarification_needed`, `technical_review`, `proposal_preparing`, `proposal_sent`, `approved`, `in_progress`, `testing`, `completed`, `rejected`, `cancelled` (клиенту — по-русски, с пояснением).

Три уровня оценки: **автоматическая предварительная** (снимок в заявке) → **проверенная администратором** (`reviewed`, `approve: false`) → **коммерческое предложение** (`approve: true`). Статусы `proposal_sent` и `approved` без утверждённой сметы сервер не ставит (409). Клиент видит предложение только в `proposal_sent` и дальше; принять может только отправленное. Отменить — пока работа не началась. Факт проекта записывается в `in_progress`/`testing`/`completed`.

## 7. Калибровка

`GET /api/admin/pricing/calibration`: по заявкам с фактом — отношение фактических часов к ожидаемым (медиана, средняя абсолютная ошибка) в целом, по работам, отраслям, видам решений, интеграциям; отклонение итоговой цены и прямых расходов. Рекомендация по работе появляется при `calibrationMinSamples` проектах (по умолчанию 3) и отклонении больше 15%; применяет её администратор кнопкой (новая версия каталога с причиной). Автоматически каталог не меняется. Ограничение: факт проекта не разбит по работам, поэтому отношение проекта относится ко всем его работам целиком.

## 8. Безопасность

- Все суммы считает сервер; тело заявки не содержит денег.
- Сметы — только через анализ владельца (гость — по своему id); заявки — по `user_id` сессии; чужое — 404.
- Админка — `requireAdmin` на сервере; скрытие ссылки на сайте ни на что не влияет.
- Клиенту не отдаются: часы и деньги по строкам, ставка, множители, резерв, внутренние заметки, назначенный администратор, факт (`pricing/views.ts`).
- Ответ модели — данные: `edited` в профиле от модели отбрасывается, незнакомые id работ не считаются, часы и цены в схеме не принимаются.
- Лимиты: 10 заявок в час и 30 правок профиля в минуту на пользователя; повтор заявки с тем же `Idempotency-Key` — та же заявка.

## 9. Тесты

- `pricing/engine.test.ts` — формулы: простая/средняя/сложная работа, приведение сложности, количество, тестирование, дедупликация общих работ, неподдерживаемые и неизвестные работы, нет работ, неопределённость и потолок, минимум и округление, сроки, выведенные работы, ежемесячные расходы.
- `pricing/store.test.ts` — хранилище в памяти и в настоящем Postgres (PGlite/`TEST_DATABASE_URL`, миграция 0012): версии, поколения, идемпотентность заявок, версии записи, журнал.
- `routes/pricing.test.ts` — сквозной путь через HTTP: гость → смета → 401 на заявку → вход → заявка со снимком и идемпотентностью → чужой пользователь 404 → админка 403 → новая версия цен (снимки не меняются) → правка профиля (новое поколение) → проверка, предложение, принятие → факт → калибровка → журнал.
- Сайт: `estimate-flow.test.tsx` (карточка сметы, подробности, гость, заявка, «Мои заявки»), `admin-pricing.test.tsx`.

## 10. Выкладка

1. Миграция `0012` применяется сама при старте (`db/sync.ts`); при сбое миграций выключаются только анализы и сметы.
2. Зайти в `/admin/pricing` → «Настройки цен»: проверить ставку, проценты, минимум, задать курс USD→KZT; «Каталог работ»: часы и статусы. Сохранить — версия 2. До этого клиенты видят сметы по начальным гипотезам (баннер в админке); выключить показ цен — снять «Показывать сметы клиентам».
3. Новых переменных окружения нет; используются прежние (`DATABASE_URL`, `ADMIN_EMAILS`/`ADMIN_API_KEY`, `DISCOVERY_ENABLED`, ключи моделей).

## 11. Что не сделано

- Отдельная сущность «бизнес» с несколькими анализами и полноценный кабинет (деплойменты, интеграции, метрики) — профиль живёт в анализе; кабинет — это «Анализы», «Помощники», «Мои заявки».
- Уведомления администраторов о новой заявке (почта/Telegram) — заявки видны в админке.
- Сравнение прогноза и факта расхода ИИ по развёрнутым решениям — факт записывается вручную в заявке.
- Казахский язык интерфейса — тексты вынесены в словари, можно добавить `kk`.
- RLS для старых таблиц.
