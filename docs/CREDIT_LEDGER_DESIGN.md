# Журнал кредитов в Postgres: проект

Составлено 11.11.2026, вторая редакция — по замечаниям владельца. Статус — **проект одобрен в принципе (вариант (b), фазы A → B → C → D); код журнала не начат и без отдельного разрешения не пишется**. Миграций нет; поведение кредитов не менялось.

## 1. Как сейчас и почему это не годится

**Как устроено:**

- `CreditService.charge` → `CreditStore.debit` (`services/credits.ts`, `store/credit-store.ts`) — синхронные операции над `Map` в памяти процесса.
- `CreditStore` построен на `DocStore` (`store/doc-store.ts`): `put()` меняет `Map`, пишет JSON-файл и запускает `upsert` в `ketner_docs` (пространство `credit_grants`) без ожидания. Ошибка записи только пишется в журнал.
- При старте (`db/sync.ts`) гранты читаются из `ketner_docs` в память.

**Следствия (по коду):**

| #   | Проблема                                                                  | Почему                                                                                                                                                                                                                        |
| --- | ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P1  | Сбой процесса теряет последние списания                                   | Запись в Postgres не ждётся; при рестарте читается то, что успело дойти                                                                                                                                                       |
| P2  | Записи в Postgres приходят не по порядку                                  | Два списания с одного гранта запускают два `upsert` полного документа (`remainingUsd`). Последним может записаться более старый — остаток в базе «откатывается» до рестарта, после рестарта такое значение становится истиной |
| P3  | Нет идемпотентности списания                                              | `charge(userId, amountUsd)` без ключа: повтор вызова — второе списание. Ключ в памяти процесса сбой не переживёт                                                                                                              |
| P4  | Второй процесс (запланированный исполнитель) держал бы свою копию остатка | Оба процесса тратили бы одни кредиты, каждый от своей копии; в базе побеждает последний `upsert`                                                                                                                              |
| P5  | Нет истории списаний                                                      | Остаток гранта перезаписывается. Сколько списано и откуда, видно только по записям использования (`UsageRecord.creditsUsd`) — тоже `ketner_docs` с той же асинхронной записью                                                 |
| P6  | `spentFromPayment` после возврата неверен                                 | Считается как `amount − remaining`; после `revokeByPayment` (`remaining = 0`) «потрачено» = всё. Сейчас вызывается только до возврата, поэтому ошибка не проявляется                                                          |

**Проверка из обзора хранения не доказывает идемпотентность биллинга.** `docs/persistence-review/idempotency-race.mjs` (сценарий «1 списание») пишет в подставную таблицу `review_charges`, а не через настоящий `CreditService`. Это проверка схемы эффектов, а не списания кредитов.

**Что сохраняется как поведение для существующих вызовов** (чат, Ketner Code, картинки, `customer_bot`):

- **Списание после ответа провайдера:** по реальной цене; `maxChargeUsd` ограничивает сумму (у бота — 30 кредитов на ответ).
- **Частичное списание:** если кредитов меньше цены, списывается остаток; разницу покрывает Ketner. Отказа нет.
- **Порядок грантов:** сначала тот, что сгорает раньше. Истёкшие и отозванные не тратятся.
- **Начисления идемпотентны по id гранта:** повторная доставка платежа второго гранта не создаёт.
- **Предварительная проверка остатка** (`balance()` до вызова модели) — синхронная, на каждый запрос; `hasPurchased()` — тоже, при определении уровня доступа.

## 2. Журнал в Postgres

### 2.1. Таблицы (эскиз, не миграция)

```sql
-- Счёт пользователя: одна строка, служит замком для всех денежных операций пользователя.
CREATE SEQUENCE credit_change_seq;
CREATE TABLE credit_accounts (
  user_id    text PRIMARY KEY,
  -- Номер последнего изменения (из общей последовательности): по нему процесс без LISTEN находит
  -- изменившиеся счета опросом (раздел 3.3, «Запуск»).
  change_seq bigint NOT NULL DEFAULT nextval('credit_change_seq'),
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX credit_accounts_change ON credit_accounts (change_seq);

-- Режим журнала: 'shadow' (фаза A — истина в памяти, журнал записывает её решения) или
-- 'authoritative' (фазы B–D — журнал решает сам). Одна строка; переключает миграция выката B.
CREATE TABLE credit_ledger_settings (
  singleton boolean PRIMARY KEY DEFAULT true CHECK (singleton),
  mode text NOT NULL CHECK (mode IN ('shadow', 'authoritative'))
);

-- Гранты: те же поля, что CreditGrant сейчас, плюс след отзыва.
CREATE TABLE credit_grants (
  id                    text PRIMARY KEY,           -- как сейчас: payment.id, `${payment.id}:bonus`, `trial:<user>`, …
  user_id               text NOT NULL REFERENCES credit_accounts (user_id),
  kind                  text NOT NULL CHECK (kind IN ('plan','bonus','free','auto','pack','admin')),
  plan_id               text,
  payment_id            text,
  amount_usd            numeric(14,6) NOT NULL CHECK (amount_usd >= 0),
  remaining_usd         numeric(14,6) NOT NULL CHECK (remaining_usd >= 0 AND remaining_usd <= amount_usd),
  granted_at            timestamptz NOT NULL,
  expires_at            timestamptz NOT NULL,
  status                text NOT NULL CHECK (status IN ('active','revoked')),
  revoked_at            timestamptz,
  revoked_remaining_usd numeric(14,6),                -- сколько сгорело при отзыве (сейчас теряется)
  note                  text,
  CHECK ((status = 'revoked') = (revoked_at IS NOT NULL))
);
CREATE INDEX credit_grants_spendable ON credit_grants (user_id, expires_at, id)
  WHERE status = 'active' AND remaining_usd > 0;
CREATE INDEX credit_grants_payment ON credit_grants (payment_id) WHERE payment_id IS NOT NULL;

-- Списание: одна строка на логический эффект.
CREATE TABLE credit_charges (
  id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  effect_id     text NOT NULL UNIQUE,                 -- логический эффект (раздел 2.3)
  user_id       text NOT NULL REFERENCES credit_accounts (user_id),
  requested_usd numeric(14,6) NOT NULL CHECK (requested_usd >= 0),
  charged_usd   numeric(14,6) NOT NULL CHECK (charged_usd >= 0 AND charged_usd <= requested_usd),
  shortfall_usd numeric(14,6) GENERATED ALWAYS AS (requested_usd - charged_usd) STORED,
  source        text NOT NULL,                        -- chat | agent | code | image | bot | execution
  usage_record_id text, run_id text, execution_id text, step_key text, model_id text,
  created_at    timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX credit_charges_user ON credit_charges (user_id, created_at);

-- Корректировки остатка гранта: явные, со знаком и причиной; только добавление.
-- reconcile    — фаза A: выравнивание журнала по памяти после сверки;
-- shadow_drift — фаза A: память списала с гранта больше, чем в нём осталось по журналу (раздел 3.3);
-- admin        — ручная правка администратором (с note и автором).
CREATE TABLE credit_adjustments (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  effect_id  text NOT NULL UNIQUE,                 -- повтор корректировки не применяется дважды
  grant_id   text NOT NULL REFERENCES credit_grants (id),
  user_id    text NOT NULL REFERENCES credit_accounts (user_id),
  amount_usd numeric(14,6) NOT NULL CHECK (amount_usd <> 0),   -- > 0 возвращает в остаток, < 0 снимает
  reason     text NOT NULL CHECK (reason IN ('reconcile', 'shadow_drift', 'admin')),
  note       text,
  created_by text NOT NULL,                        -- 'system:reconcile', 'system:shadow', id администратора
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX credit_adjustments_grant ON credit_adjustments (grant_id);

-- Из каких грантов списано: основа для аудита, возврата и проверки инвариантов.
CREATE TABLE credit_charge_allocations (
  charge_id  bigint NOT NULL REFERENCES credit_charges (id),
  grant_id   text   NOT NULL REFERENCES credit_grants (id),
  amount_usd numeric(14,6) NOT NULL CHECK (amount_usd > 0),
  PRIMARY KEY (charge_id, grant_id)
);
CREATE INDEX credit_charge_allocations_grant ON credit_charge_allocations (grant_id);
```

Оформление — по правилам из [SECURITY_PRIVILEGE_AUDIT.md](SECURITY_PRIVILEGE_AUDIT.md):

- RLS без политик;
- `REVOKE ALL … FROM anon, authenticated`;
- `credit_charges`, `credit_charge_allocations` и `credit_adjustments` — только добавление (триггер, как `execution_events`);
- функции журнала (если списание оформлено функцией в базе) — `REVOKE EXECUTE … FROM PUBLIC, anon, authenticated` сразу после создания.

Деньги — `numeric(14,6)`, как `round6` сейчас: точность $0.000001 = 0,001 кредита.

**Инварианты** (проверяются запросом сверки и тестами):

|     | Инвариант                                                                                                                                       |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| I1  | `0 ≤ remaining_usd ≤ amount_usd` (ограничение)                                                                                                  |
| I2  | Для каждого гранта: `amount_usd − Σ allocations + Σ adjustments − coalesce(revoked_remaining_usd, 0) = remaining_usd` (корректировки со знаком) |
| I3  | Для каждого списания: `Σ allocations = charged_usd ≤ requested_usd`                                                                             |
| I4  | Одно списание на `effect_id` (уникальность)                                                                                                     |
| I5  | Распределение только на гранты, действующие и не истёкшие в момент списания                                                                     |

### 2.2. Списание — одна транзакция

`ledger_charge(effect_id, user_id, requested_usd, source, refs, now)`. Функция в базе или та же последовательность в коде сервера — решается при реализации. `now` — параметр для тестов, по умолчанию `now()` транзакции.

```
BEGIN;
1. INSERT INTO credit_accounts (user_id) VALUES ($user) ON CONFLICT DO NOTHING;
   SELECT 1 FROM credit_accounts WHERE user_id = $user FOR UPDATE;     -- замок пользователя
2. SELECT * FROM credit_charges WHERE effect_id = $effect;
   если есть: user_id и requested_usd совпадают -> вернуть сохранённый результат (charged_usd, allocations), COMMIT;
              не совпадают -> ошибка «effect_id использован с другими параметрами», ROLLBACK.
3. SELECT id, remaining_usd FROM credit_grants
     WHERE user_id = $user AND status = 'active' AND remaining_usd > 0 AND expires_at > $now
     ORDER BY expires_at, id;                                           -- строки уже защищены замком счёта
4. Распределить requested_usd по порядку: take = min(remaining, left).
   UPDATE credit_grants SET remaining_usd = remaining_usd - take WHERE id = …;
   INSERT INTO credit_charge_allocations …;
5. INSERT INTO credit_charges (effect_id, …, requested_usd, charged_usd = Σ take, …);
COMMIT;  -> вернуть { charged_usd, duplicate: false }
```

Замок счёта ставится раньше проверки `effect_id`. Поэтому два одинаковых запроса не могут оба не найти строку и оба списать: второй ждёт замка и на шаге 2 видит строку первого. Строки грантов отдельно не блокируются: все изменения грантов пользователя идут под тем же замком, порядок один — взаимных блокировок нет.

| Случай                                                   | Поведение                                                                                                                                      |
| -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Тот же `effect_id` повторно                              | Возвращается исходный результат (`charged_usd` и распределение), остатки не меняются                                                           |
| Одновременные дубликаты (два процесса, один `effect_id`) | Второй ждёт замка счёта, видит списание первого и возвращает его результат. Если первый откатился — второй списывает сам. Ровно одно списание  |
| Одновременные разные списания одного пользователя        | Выполняются по очереди под замком; сумма списаний не превышает остатка; остаток не уходит ниже нуля (ограничение I1)                           |
| Остатка меньше, чем `requested_usd`                      | Списывается всё, что есть; `shortfall_usd` = разница (её покрывает Ketner — как сейчас). Ошибки нет                                            |
| Остатка нет                                              | Строка списания с `charged_usd = 0` (видно, сколько Ketner покрыл); гранты не меняются                                                         |
| Грант истёк (`expires_at ≤ now`)                         | Не участвует. Его остаток остаётся в строке как история, в баланс не входит. Граница как сейчас: истёкшим считается грант с `expires_at ≤ now` |
| Грант отозван                                            | Не участвует (`status = 'revoked'`)                                                                                                            |

### 2.3. Логический `effect_id`

Ключ должен одинаково получаться при каждом повторе одного и того же списания:

| Источник                                           | `effect_id`                                                                                      | Откуда повтор                                                                                                                                            |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Исполнение платформы (шаг модели)                  | `exec:<execution_id>:<step_key>`                                                                 | Повтор шага; повтор узла n8n; рестарт исполнителя. Совпадает с ключом `execution_effects` ([PERSISTENCE_DESIGN.md](PERSISTENCE_DESIGN.md), 4.1)          |
| Чат, бот, агент (`gateway.ts`, `agent-gateway.ts`) | `usage:<id записи использования>` — id создаётся до списания и тот же пишется в `UsageRecord.id` | Повтора вызова в процессе нет; ключ нужен для повторной попытки записи после сбоя связи с базой (раздел 3.4) и для связи списание ↔ запись использования |
| Ketner Code (`code/agent-runner.ts`)               | `code:<runId>:<step>:<attempt>`                                                                  | То же                                                                                                                                                    |
| Картинки (`images/service.ts`)                     | `image:<id картинки>`                                                                            | То же                                                                                                                                                    |

### 2.4. Начисления и возвраты

**Начисление** `ledger_grant(input)`:

- `INSERT … ON CONFLICT (id) DO NOTHING RETURNING *`; если строка не вставлена — вернуть существующую с `duplicate: true` (как сейчас);
- под замком счёта.

**Возврат** `revokeByPayment(paymentId)` — под замком счёта владельца платежа:

```
UPDATE credit_grants SET status = 'revoked', revoked_at = now(),
       revoked_remaining_usd = remaining_usd, remaining_usd = 0
 WHERE payment_id = $1 AND status = 'active' RETURNING *;
```

- Повторный вызов ничего не меняет и возвращает те же гранты (идемпотентно).
- Уже списанное по распределениям не возвращается — как сейчас: потраченные кредиты потрачены.

**`spentFromPayment(paymentId)`** = `Σ allocations` по грантам платежа. Это точное значение и до, и после отзыва (исправляет P6, на текущее правило возврата не влияет).

**Списание и возврат одновременно** идут по очереди под замком счёта:

- если возврат первым — списание не видит отозванный грант;
- если списание первым — возврат отзывает остаток.

Двойного учёта нет.

## 3. Источник истины: во время перехода и после

### 3.1. Подпись `charge` должна стать асинхронной

**Вывод: да, `charge` должен стать асинхронным** (`Promise<ChargeResult>`). Списание не может считаться сделанным, пока транзакция не зафиксирована. Синхронная подпись оставляет два пути, и оба плохие:

- вернуть число до фиксации — тогда списание снова «в памяти» (P1–P4);
- блокировать поток Node — так не делают.

**Цена изменения** (по коду):

| Место                                                       | Сейчас                                                                                                | Что меняется                                                          |
| ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| `ai/gateway.ts:1075` (чат, бот, задачи Discovery и Builder) | `this.credits.charge(...)` внутри `async stream()`                                                    | `await`; `effect_id` = id записи использования, созданный до списания |
| `ai/agent-gateway.ts:690`                                   | `charge` внутри синхронного `private recordUsage()`, который вызывается в `async execute()` (3 места) | `recordUsage` → `async`, 3 вызова → `await`                           |
| `code/agent-runner.ts:950`                                  | внутри цикла в `async run()`                                                                          | `await`                                                               |
| `images/service.ts:397`                                     | внутри `async generate()`                                                                             | `await`                                                               |
| `services/credits.ts`                                       | `CreditLedger.charge(): number`                                                                       | `charge(): Promise<ChargeResult>`; `onCharged` — после фиксации       |
| `services/credits-fixture.ts`, тестовые подстановки         | синхронный `charge`                                                                                   | `await`; ≈ 15 вызовов в 5 тестовых файлах                             |

Все четыре места уже в асинхронных функциях, поэтому изменение механическое. Задержка — одна транзакция к базе (несколько запросов) после ответа модели, до записи использования. Пользователь увидит её в последнем событии потока с `creditsUsd`, а не в ответе модели. Задержку до Supabase от Render — **не измерено**; измерить в фазе A.

**Чтение остается синхронным.** Синхронные чтения `balance()` и `hasPurchased()` вызываются более чем из десяти мест, часть из них — синхронный код (определение уровня доступа, отчёты, Telegram). Им достаточно **кэша в памяти**, обновляемого из базы. Кэш — только подсказка:

- им пользуются предварительная проверка «хватит ли на запрос» и интерфейс;
- сколько списать, решает только транзакция журнала;
- устаревший кэш в худшем случае пропустит один запрос при кончившемся остатке, и тогда Ketner покроет его цену. Это уже возможно сейчас при одновременных запросах.

**`ensureGrants` уходит из `balance()`.** Сейчас `balance()` при чтении **создаёт** гранты (пробные, `auto` для прежних подписчиков) и переносит старые пакеты (`migrateLegacy`) — это запись. В журнале:

- `ensureGrants(userId, plan)` становится асинхронным;
- вызывается: при входе пользователя и в обработчике запроса после определения тарифа (не чаще раза в сутки на пользователя в процессе), а также внутри `charge` перед распределением;
- id грантов детерминированы (`trial:<user>`, `auto:<user>:<plan>:<day>`), поэтому вызовы из нескольких процессов безопасны;
- `migrateLegacy` — разовая перекладка данных при переходе, а не ленивый перенос при чтении.

### 3.2. Варианты объёма

**(a) Журнал только для исполнений платформы, существующие вызовы без изменений.**

Пул кредитов у пользователя один, поэтому в одних и тех же грантах оказываются два писателя: журнал (исполнения) и `CreditStore` в памяти (чат, Code, картинки, бот). Чтобы остаток не расходился, нужно одно из двух:

- **разделить пул** (отдельные кредиты на исполнения) — это изменение продукта и цен;
- **сделать журнал единственным хранилищем грантов**, а старые вызовы — отложенной записью: синхронный `charge` уменьшает кэш и ставит в очередь `ledger_charge(effect_id)`, которая выполняется после.

Второй путь — это фаза A ниже плюс исполнения поверх неё. Как конечное состояние он плох:

- списания старых вызовов по-прежнему теряются при сбое (P1);
- сумма, которую старый вызов записал в `UsageRecord.creditsUsd`, может разойтись с фактически списанной, если исполнение в другом процессе успело потратить остаток.

**(b) Перенести кредиты в Postgres полностью.** Журнал — единственная истина для всех вызовов; `charge` асинхронный (3.1); чтения из кэша.

**Рекомендация: (b), по фазам A → B → C → D (одобрено 11.11.2026).** Вариант (a) как конечное состояние не рекомендую: он оставляет P1 для основных денег (чат и Code) и две разные семантики списания. Его полезная часть — теневая запись — входит в фазу A.

### 3.3. Фазы перехода

| Фаза                          | Истина                             | Что делается                                                                                                                                                                                                                                                                                                                                                                                                           | Выход из фазы                                                                                                           |
| ----------------------------- | ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| **A. Тень** (1 выкат)         | Память (`CreditStore`), как сейчас | Таблицы журнала, режим `shadow`. Разовая перекладка грантов из `ketner_docs/credit_grants` и старых пакетов. Каждое начисление, списание и отзыв **дополнительно** записывается в журнал после операции в памяти (асинхронно, с `effect_id`, повторы безопасны). **Журнал записывает то, что сделала память**, а не распределяет сам (раздел 3.3.1). **Перекрытие процессов при выкате.** Render держит старый экземпляр, пока новый не пройдёт проверку здоровья: какое-то время работают оба.

- **Выкат B поверх A.** Миграция выката B переключает режим журнала на `authoritative`. Старый процесс (истина — память) продолжает теневую запись. В режиме `authoritative` журнал не применяет присланное распределение по грантам, а выполняет обычное списание (2.2) суммы, которую старый процесс фактически списал в памяти, с тем же `effect_id`. Потерь нет; на время перекрытия остаток в памяти старого процесса может быть выше фактического, то есть возможен тот же пропуск одного запроса, что описан выше.
- **Выкат A поверх текущего `main`.** Разовая перекладка читает `ketner_docs`, а старый процесс в эти секунды ещё пишет туда. Поэтому перекладка идемпотентна по id гранта, а после окончания перекрытия выполняется сверка память ↔ журнал. Новый процесс — единственный, его память — истина. Расхождение по гранту журнал выравнивает строкой `credit_adjustments` с причиной `reconcile` и `effect_id = reconcile:<grant>:<номер сверки>`; инвариант I2 учитывает её явно.

#### 3.3.1. Теневая запись (фаза A): журнал повторяет решение памяти

Если бы журнал в тени сам распределял запрошенную сумму, он расходился бы с памятью по построению:

- у журнала другой порядок времени (запись асинхронная);
- он может считать грант истёкшим, когда память его ещё тратила;
- он не знает о частичном списании.

Поэтому:

- `CreditStore.debit` получает внутренний вариант, который возвращает **распределение**: какой грант на сколько уменьшен. Подпись и поведение `debit`/`charge` для вызывающих не меняются;
- теневая запись передаёт в журнал `effect_id`, запрошенную сумму, **фактически списанную** памятью сумму и это распределение;
- в режиме `shadow` журнал под замком счёта:
  - вставляет строку `credit_charges` с `requested_usd` и `charged_usd` из памяти;
  - вставляет распределение **как есть**, не проверяя сроки и порядок грантов;
  - уменьшает остатки на эти суммы;
- если по журналу в гранте осталось меньше, чем списала память (расхождение уже было), перед уменьшением добавляется корректировка `shadow_drift` на недостающую сумму. Остаток не уходит ниже нуля, I2 выполняется, расхождение видно в `credit_adjustments` и в отчёте сверки;
- грант, которого в журнале нет (начисление ещё не дошло), создаётся из теневой записи начисления; списание ждёт его в очереди теневых записей (порядок записей одного пользователя сохраняется).

**Критерий выхода из фазы A:** за 2–3 дня ни одной корректировки `shadow_drift` и `reconcile`, кроме объяснённых (сбой процесса, перекрытие при выкате).

**Запуск в фазе B:**

1. Раннер миграций.
2. Чтение всех действующих и не истёкших грантов из журнала в кэш. Объём ≈ число пользователей × несколько грантов; если станет большим — ленивая загрузка по пользователю при первом обращении через асинхронный путь запроса.
3. Подписка `LISTEN credit_changed`: другие процессы после фиксации делают `NOTIFY` с `user_id`, кэш этого пользователя перечитывается. Без этого второй процесс видит устаревший остаток (только подсказка, не деньги).

**Ограничение: `LISTEN/NOTIFY` работает только через сессионное подключение.**

- Подходят прямое подключение `db.<ref>.supabase.co:5432` или пулер Supavisor в режиме сессии (порт 5432).
- В режиме транзакций (порт 6543) соединение сервера между транзакциями отдаётся другим клиентам: подписка `LISTEN` не сохраняется, и уведомления не приходят. Ошибки при этом может не быть — кэш просто тихо устаревает.

Что предусмотрено:

- **Отдельное подключение для `LISTEN`.** Сессионное, одно на процесс, вне общего пула. Адрес — переменная `DATABASE_LISTEN_URL`, по умолчанию `DATABASE_URL`.
- **Проверка при старте.** Процесс делает `NOTIFY` себе и ждёт его не дольше 5 с. Если уведомление не пришло (например, адрес переведён на порт 6543), процесс:
  - пишет в журнал предупреждение;
  - переходит на опрос: раз в 5 с читает `credit_accounts` с `change_seq` больше последнего виденного и перечитывает эти счета;
  - помечает в `/api/admin/credits/health` режим `poll` вместо `listen`.
- **Если весь `DATABASE_URL` переведут на пулер транзакций (6543):**
  - сами транзакции журнала работают — замок счёта и `FOR UPDATE` действуют внутри транзакции;
  - для postgres.js нужен `prepare: false`;
  - уведомления — только через `DATABASE_LISTEN_URL` на сессионном подключении, иначе действует опрос;
  - отдельному процессу-исполнителю в режиме опроса списывать нельзя (раздел 5, п. 4).

### 3.4. База недоступна в момент списания

Провайдер уже ответил, деньги Ketner потрачены, а транзакция не прошла. Сейчас этого случая нет: списание в памяти не падает.

Предложение (одобрено 11.11.2026: ограниченная очередь повторов в процессе):

- запись использования создаётся с `creditsUsd = null` и признаком «списание в очереди»;
- `ledger_charge` с тем же `effect_id` повторяется с нарастающей паузой: 1, 2, 4, … до 60 с, без ограничения числа попыток, пока запись в очереди;
- повтор безопасен (2.2, шаг 2);
- когда списание прошло, запись использования получает `creditsUsd`;
- пока очередь не пуста, предварительная проверка для пользователя учитывает сумму его записей в очереди.

**Границы очереди** (на процесс):

| Граница                     | Значение            | Почему                                                           |
| --------------------------- | ------------------- | ---------------------------------------------------------------- |
| Записей всего               | 1 000               | Порядка часа работы при текущей нагрузке; память — килобайты     |
| Сумма всего                 | $5 (5 000 кредитов) | Ограничивает, сколько Ketner может не взыскать за один сбой базы |
| Записей одного пользователя | 50                  | Один активный пользователь не занимает всю очередь               |

**Переполнение** (любая граница превышена):

1. Новое списание, которое не помещается, **не теряется молча**:
   - в журнал сервера пишется ошибка `credit_charge_dropped` с `effect_id`, `user_id` и суммой;
   - сумма прибавляется к счётчику «не взыскано из-за переполнения»;
   - запись использования остаётся с `creditsUsd = null` и признаком `charge_dropped` — по ней сверка найдёт списание позже (раздел 3.5).
2. Пока очередь заполнена больше чем на 80 %, **новые платные запросы отклоняются** с ответом 503 «биллинг временно недоступен»: и у пользователя, превысившего свою границу, и у всех при общей границе. Бесплатная модель продолжает работать.
3. Записи уже в очереди продолжают повторяться. Когда база вернулась и очередь опустела ниже 80 %, приём платных запросов возобновляется сам.

Сбой процесса теряет только записи очереди; их тоже находит сверка — записи использования без строки `credit_charges`.

**Где видно, сколько покрыл Ketner:**

| Что                                                                      | Где                                                                                                                   |
| ------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| Очередь сейчас: записей, сумма, возраст старейшей, режим `listen`/`poll` | `GET /api/admin/credits/health` (только администратор) и строка в журнале сервера раз в минуту, пока очередь не пуста |
| Не взыскано из-за переполнения (с запуска процесса)                      | Тот же ответ: счётчик и сумма `credit_charge_dropped`                                                                 |
| Не хватило остатка (частичные списания)                                  | `Σ credit_charges.shortfall_usd` за день и месяц — в том же ответе и в админке                                        |
| Потеряно при сбоях процесса                                              | Отчёт сверки: записи использования с `creditsUsd = null` без строки `credit_charges`, сумма по их `estimatedCost`     |

### 4.3. Тесты, которые должны доказать

Все тесты — на **настоящем `CreditService`** и **настоящем Postgres** (`TEST_DATABASE_URL`, стенд 16 и 17), без подставных таблиц.

1. **Одно списание на эффект:** `charge` с тем же `effect_id` 2 и 50 раз подряд → одна строка `credit_charges`, одинаковый результат, остаток уменьшился один раз.
2. **Одновременные дубликаты:** 2 процесса Node × 20 параллельных `charge` с одним `effect_id` → ровно одно списание.
3. **Одновременные разные списания:** 2 процесса × 100 списаний одного пользователя при остатке меньше суммы → `Σ charged = min(Σ requested, начальный остаток)`, остаток ≥ 0, I1–I3 выполняются.
4. **Частичный остаток:** списание больше остатка → списан весь остаток, `shortfall` верный. Совпадает с текущим `CreditStore.debit` на тех же данных (сравнительный тест старой и новой реализации на 1000 случайных последовательностей, допуск 1e-6).
5. **Сроки:** грант с `expires_at = now` не тратится; порядок — по `expires_at`, затем `id`.
6. **Возвраты:**
   - `revokeByPayment` дважды → тот же результат;
   - одновременно с потоком списаний → инварианты выполняются, после отзыва грант не тратится;
   - `spentFromPayment` до и после отзыва одинаков.
7. **Начисления:** повторная доставка платежа → `duplicate: true`, один грант; одновременная доставка из двух процессов → один грант.
8. **Убийство процесса между шагами** (дочерний процесс, `SIGKILL` по метке в коде):
   - после вставки списания, до `COMMIT` → списания нет; повтор с тем же `effect_id` списывает один раз;
   - после `COMMIT`, до записи использования → повтор возвращает исходный результат, второго списания нет;
   - фаза C: после фиксации списания, до фиксации эффекта невозможно, так как это одна транзакция — проверить, что откат транзакции откатывает и то и другое.
9. **Старт:** кэш после рестарта равен журналу; `NOTIFY` от второго процесса обновляет кэш.
10. **Существующие тесты** чата, Code, картинок, бота, биллинга и возвратов проходят без изменения ожиданий (меняется только `await`).
11. **Перекладка и откат:**
    - перекладка из `ketner_docs` даёт тот же баланс по каждому пользователю;
    - скрипт отката B → A восстанавливает `ketner_docs`, по которому старый код показывает тот же баланс.
12. **Пробный грант до первой проверки (регрессия переноса `ensureGrants` из `balance()`):**
    - новый пользователь: после входа (Better Auth, Telegram, вход по ключу API) и до первой предварительной проверки остатка или первого запроса к модели в журнале есть грант `trial:<user>`;
    - `balance()` у этого пользователя сразу показывает пробные кредиты;
    - первый платный запрос не получает отказ «нет кредитов».
13. **Тень (фаза A):**
    - журнал повторяет распределение памяти байт в байт, включая списание с гранта, который журнал считал бы истёкшим;
    - искусственное расхождение даёт ровно одну корректировку `shadow_drift`, остаток не уходит ниже нуля, I2 выполняется.
14. **Корректировки:** повтор `reconcile` с тем же `effect_id` не применяется второй раз; I2 с корректировками выполняется на случайных последовательностях.
15. **Режимы при перекрытии выкатов:** теневая запись в режиме `authoritative` превращается в обычное списание суммы памяти с тем же `effect_id`; повтор не списывает второй раз.
16. **`LISTEN` и опрос:**
    - через сессионное подключение уведомление приходит, режим `listen`;
    - через подключение без сохранения сессии (модель пулера транзакций: подписка теряется) проверка при старте переводит процесс в режим `poll`, и изменение из другого процесса попадает в кэш за ≤ 5 с.
17. **Очередь повторов:**
    - база недоступна (сеть отключена в тесте) → записи копятся, после возврата базы проходят ровно по одному разу;
    - границы 1 000 записей, $5 и 50 на пользователя;
    - при переполнении — `credit_charge_dropped` и рост счётчика, ответ 503 на новые платные запросы, бесплатная модель отвечает;
    - после разгрузки ниже 80 % приём возобновляется;
    - `/api/admin/credits/health` показывает размер, сумму, отброшенное и `shortfall`.

## 5. Что должно быть верно, прежде чем отдельный процесс-исполнитель спишет кредиты

1. **Журнал — единственная истина для всех списаний и начислений (фаза B завершена).** Ни один процесс не меняет гранты в памяти.
2. **Списание исполнителя идемпотентно по `exec:<execution>:<step>`** и фиксируется в одной транзакции с эффектом шага (фаза C).
3. **Исполнитель не принимает денежных решений по кэшу.** Предварительную проверку остатка он читает из базы или делает резерв (п. 5).
4. **Кэши остальных процессов обновляются по `NOTIFY`** после списаний исполнителя. Подключения `LISTEN` всех процессов — сессионные (прямое или пулер в режиме сессии, порт 5432), проверка при старте прошла (режим `listen`). В режиме `poll` исполнитель не запускается.
5. **Длинным исполнениям нужен резерв**, чтобы два процесса не потратили один остаток параллельно. Перед запуском резервируется потолок исполнения, после — расчёт по факту. Образец уже есть в коде: бюджет Discovery `discovery_budget_reservations` (`held → running → settled | released`, истёкший резерв закрывается). Для существующих вызовов резерв не вводится: они остаются с оплатой после ответа.
6. **Записи использования исполнителя пишутся в Postgres с подтверждением**, а не через асинхронное зеркало `ketner_docs`. Иначе списание есть, а объяснения в кабинете нет.
7. **Побочные действия после списания идемпотентны между процессами.** Пример: письмо «кредиты на исходе» (`services/low-credits-notifier.ts`) хранит отметку об отправке в `ketner_docs` через память процесса — два процесса отправят два письма.
8. **Время — из базы.** Сроки грантов сравниваются с `now()` транзакции, а не с часами процесса.
