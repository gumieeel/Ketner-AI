## 1. Что меняется в архитектуре

1. **n8n больше не планируется.** Причины остаются в истории: лицензия Sustainable Use License и платные Enterprise/Embed для многоарендного SaaS с учётными данными клиентов, Node 24, отдельный сервер.
2. **Исполнитель workflow — сменный адаптер.** Ketner хранит свою модель процесса (`KetnerWorkflowDefinition`) и говорит с исполнителем через `WorkflowEngineAdapter`. Кандидатов два:
   - **встроенный исполнитель Ketner** на очереди задач в Postgres;
   - **Activepieces** как внешний адаптер для «длинного хвоста» интеграций.
3. **Activepieces — только внутренняя инфраструктура.** Его интерфейс, редактор и встраиваемый конструктор клиенту не показываются.
4. **Mastra не вводится по умолчанию.** Сначала сравнение с существующим `AgentGateway` на прототипе (T4.0).
5. **Единственная точка вызова моделей — AIGateway.** ИИ-интеграции Activepieces (свои AI-провайдеры, агенты, база знаний, MCP) не используются: они ходят к моделям в обход учёта Ketner.

## 2. Подходит ли Activepieces технически

### Что есть и подходит

| Возможность                   | Что проверено                                                                                                                                                                                                                                            |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Создание и настройка по API   | `POST /v1/flows` — создать; `POST /v1/flows/{id}` — применить операцию (`IMPORT_FLOW`, `LOCK_AND_PUBLISH`, `CHANGE_STATUS`, `ADD_ACTION`, `UPDATE_TRIGGER` и др.); `GET/DELETE /v1/flows/{id}`                                                           |
| Запуск                        | Через вебхук-триггер: `/v1/webhooks/{flowId}` (асинхронно) и `/v1/webhooks/{flowId}/sync` (с ответом, по умолчанию до 30 с — `AP_WEBHOOK_TIMEOUT_SECONDS`). Отдельной команды «выполнить flow» в публичном API нет                                       |
| Статус и результат            | `GET /v1/flow-runs`, `GET /v1/flow-runs/{id}`, `GET /v1/flow-runs/count-by-status`, `POST /v1/flow-runs/cancel`                                                                                                                                          |
| Повтор                        | В коде есть `POST /v1/flow-runs/{id}/retry` (со стратегией) и массовый `POST /v1/flow-runs/retry`; в публичном `openapi.json` их нет, то есть это внутренний API                                                                                         |
| Учётные данные                | `POST/GET /v1/app-connections`, `GET/POST/DELETE /v1/app-connections/{id}`, ссылка OAuth2 `POST /v1/app-connections/oauth2/authorization-url`                                                                                                            |
| Устойчивое исполнение         | Журнал прогона с контрольными точками (каждые 15 с и на каждом завершённом шаге), после сбоя повторяется только незавершённый шаг; очередь BullMQ в Redis, гарантия «хотя бы один раз»                                                                   |
| Паузы                         | Waitpoints: шаги «Wait for Approval» и «Delay» не тратят лимит времени; пауза живёт до 30 дней (`AP_PAUSED_FLOW_TIMEOUT_DAYS`)                                                                                                                           |
| Лимиты                        | Прогон до 600 с (`AP_FLOW_TIMEOUT_SECONDS`), 1 ГБ памяти на воркер, хранение данных прогонов 30 дней, тело вебхука 25 МБ, лог прогона 50 МБ; лимиты частоты по проектам (`AP_PROJECT_RATE_LIMITER_ENABLED`, по умолчанию выключены)                      |
| Изоляция исполнения           | `AP_EXECUTION_MODE=SANDBOX_CODE_ONLY` — шаги Code в отдельном V8-изоляте (128 МБ, без `require`, файлов и npm), контейнер без привилегий; документация называет его режимом для многоарендной работы. `AP_WORKER_CONCURRENCY=1` — один flow на контейнер |
| Свои интеграции на TypeScript | Фреймворк pieces (npm-пакеты); их можно опубликовать в npm или собрать в свой образ из частного форка                                                                                                                                                    |

### Ограничения, которые влияют на Ketner

1. **Публичный API с ключами — только в Platform/Enterprise.** Цитата из `docs/endpoints/overview.mdx`: API-ключи создаются в панели платформы, «which is only available in the Platform and Enterprise editions». В коде модуль `apiKeyModule` регистрируется только для ENTERPRISE и CLOUD. В Community Edition контроллеры принимают только участника `USER`, то есть JWT вошедшего человека. Сервер-сервер интеграция с CE возможна только через **внутренний, недокументированный** API от имени служебного пользователя. Он может меняться без предупреждения.
2. **Многоарендность — коммерческие функции.** Участники проектов, роли, наборы интеграций на проект (piece sets), глобальные подключения, журнал аудита, менеджеры секретов, платформенные вебхуки, SSO и одобрение публикации flow (`flowApprovalModule`) регистрируются только в ENTERPRISE и CLOUD.
3. **Нельзя ограничить набор интеграций в CE.** Список разрешённых интеграций и действий (`platformPieceModule`, `pieceSetModule`) — Enterprise. В CE доступны все pieces, включая Code. Защита держится только на компиляторе Ketner: он не генерирует запрещённые шаги, и доступ к интерфейсу Activepieces только у админов Ketner.
4. **Частные интеграции — платная функция** (`docs/build-pieces/sharing-pieces/private.mdx`). В CE свои pieces ставятся из публичного npm или вшиваются в собственный образ из форка.
5. **Встраивание конструктора и подключений (Embed SDK, managed auth через JWT) — Enterprise.** Ketner это и не нужно: интерфейс свой.
6. **Изоляция арендаторов на уровне данных** обеспечивается фильтром по `projectId`/`platformId` в коде API, а не песочницей (`docs/install/guarantees/execution-isolation.mdx`). В CE на одном проекте все учётные данные всех клиентов Ketner лежат в одном проекте: изоляцию придётся держать на стороне Ketner.
7. **Свои вызовы моделей.** У Activepieces есть AI-провайдеры, агенты, база знаний, MCP и учёт AI-расхода. Если ими пользоваться, вызовы моделей идут мимо AIGateway. Решение — запретить AI-pieces и вызывать модели только через Ketner (HTTP-шаг к API Ketner или свой piece).
8. **Инфраструктура.** Для прода нужны app, воркеры (0,5 vCPU / 1 ГБ на каждый одновременный flow), Postgres (своя база, не схема Ketner), Redis и S3; документация называет S3 обязательным для прода. На бесплатном Render это не запустить: нужен отдельный небольшой кластер или несколько платных сервисов.

**Вывод:** технически Activepieces — зрелый исполнитель с устойчивыми прогонами, песочницей и сотнями интеграций. Но всё, что нужно для безопасной многоарендной работы под управлением Ketner, находится в коммерческой части: API-ключи, проекты на клиента, список разрешённых интеграций, аудит. В CE остаётся одноарендная схема с недокументированным API.

## 3. Лицензия и совместимость с SaaS

**Проверено:**

- Корневой `LICENSE`: всё вне `packages/ee/` и `packages/server/api/src/app/ee` — MIT (Expat). Сторонние компоненты — под своими лицензиями.
- `packages/ee/LICENSE` (Enterprise License): этот код можно использовать в production только при согласии с Activepieces Subscription Terms (или по другому договору) и при действующей Enterprise-лицензии на нужное число мест. Для разработки и тестов он бесплатен. Копировать, публиковать, распространять, сублицензировать и продавать его запрещено.
- `docs/about/license.mdx`: использование enterprise-функций в self-hosted установке требует лицензии Activepieces.
- Встраивание и частные pieces помечены в документации как платные / Enterprise.
- Pieces в `packages/pieces/` — MIT по общему правилу корневого `LICENSE`. Лицензии отдельных pieces поштучно не проверялись.

## 4. Activepieces против своего лёгкого исполнителя

| Критерий                 | Activepieces CE                                                     | Activepieces Enterprise        | Свой исполнитель Ketner (Postgres)                                                        |
| ------------------------ | ------------------------------------------------------------------- | ------------------------------ | ----------------------------------------------------------------------------------------- |
| Лицензия                 | MIT + открытый вопрос L1                                            | Договор, цена неизвестна       | Свой код, вопросов нет                                                                    |
| Число интеграций         | Сотни готовых pieces                                                | То же                          | Только то, что написали сами (на старте 3–5)                                              |
| API для управления       | Внутренний, без ключей, может меняться                              | Публичный, с ключами           | Свой, стабильный                                                                          |
| Изоляция арендаторов     | Один проект на всех — держит Ketner                                 | Проект на клиента, роли, аудит | `user_id` в каждой таблице, как в остальном Ketner                                        |
| Список разрешённых шагов | Нет (Code доступен) — только дисциплина компилятора                 | Piece sets                     | По построению: исполнитель умеет только свои шаги                                         |
| Учёт и бюджеты           | Свой AI-учёт мешает; бюджеты Ketner — снаружи                       | То же                          | Через `CreditService` и журнал исполнений                                                 |
| Устойчивость             | Сильная: контрольные точки, очередь, повторы                        | То же                          | Надо сделать: очередь `FOR UPDATE SKIP LOCKED`, идемпотентность шагов, повторы с потолком |
| Инфраструктура           | App + воркеры + Redis + своя Postgres + S3                          | То же                          | Отдельный процесс-воркер этого же репозитория + текущая Postgres                          |
| Сложность первой версии  | Средняя: компилятор, служебный пользователь, синхронизация статусов | Средняя + договор              | Средняя: очередь, 5–7 видов шагов, вебхуки, расписание                                    |
| Риск привязки            | Средний (за адаптером)                                              | Средний + коммерческий         | Нет                                                                                       |

Вывод: для первых сценариев Ketner (заявка с сайта → проверка → агент → запись → уведомление; ежедневный отчёт; напоминание с эскалацией) нужно 5–7 видов шагов и 3–5 интеграций. Свой исполнитель покрывает это без лицензионных вопросов и лишней инфраструктуры. Activepieces окупается, когда понадобится много разных интеграций, и только при понятной лицензии.

## 5. Рекомендуемая архитектура

```
Сайт Ketner (свой интерфейс)
        │
API Ketner (Express): Discovery → SolutionSpec → AgentSpec / KetnerWorkflowDefinition
        │                        │
        │              Проверки кодом: схема, реестр возможностей, права, риск, бюджет
        │                        │
   Агенты:                 WorkflowEngineAdapter
   AgentGateway или          ├── KetnerNativeEngine (по умолчанию): очередь в Postgres, воркер
   Mastra (по итогам T4.0)   └── ActivepiecesAdapter (опционально, за флагом, после L1–L3)
        │                        │
     AIGateway  ◄────────────────┘  все вызовы моделей, учёт, кредиты, бюджеты
        │
   PostgreSQL (Supabase): решения, версии, исполнения, события, очередь, подключения (шифрование)
   Pricing Engine: смета, бюджеты исполнения, факт против оценки
```

Правила:

- **Определение процесса** хранится в Ketner. Исполнитель получает только скомпилированную, проверенную версию.
- **Компилятор работает по белому списку:** виды шагов, интеграции, операции, ссылки на подключения. Шаги с произвольным кодом (Code piece, HTTP на любой адрес) не генерируются никогда. Модель не пишет ни JS, ни сырой JSON исполнителя.
- **Учётные данные клиентов** хранятся в Ketner (AES-256-GCM, общий модуль секретов). Если используется Activepieces, подключение создаётся там только при развёртывании, именуется по клиенту, а секрет не возвращается на сайт, в логи и в промпты.
- **Модели** вызываются только через API Ketner (вызов агента подписанным запросом). AI-pieces Activepieces запрещены.
- **Статусы** исполнителя переводятся в статусы Ketner (Готовится / Нужно подключение / Активна / Требует внимания / Пауза / Ошибка). Внутренние статусы клиенту не показываются.
- **Одобрения** чувствительных действий — сервис одобрений Ketner. Встроенные Approval/Delay исполнителя допустимы только как механизм ожидания, решение принимает Ketner.
- **Бюджеты:** до запуска — проверка кодом (`CreditService` + лимиты решения). После — фактический расход из журнала исполнений. Повторы ограничены числом.

## 6. Обновлённый план (кратко)

Полная таблица задач — в [TRANSFORMATION_TASKS.md](TRANSFORMATION_TASKS.md), этап 6. Порядок:

1. **W0** — письмо в Activepieces (L1–L5); решение по инфраструктуре воркера.
2. **W1** — `KetnerWorkflowDefinition` и статическая проверка.
3. **W2** — `WorkflowEngineAdapter` и встроенный исполнитель на Postgres: очередь, идемпотентность, повторы, вебхуки, расписание, ожидание одобрения.
4. **W3** — первый сценарий целиком на своём исполнителе (заявка с сайта → агент → запись → уведомление).
5. **W4** — прототип адаптера Activepieces в локальном Docker (CE, `SANDBOX_CODE_ONLY`): компилятор в flow, служебный пользователь, запуск через вебхук, синхронизация статусов, повтор. Только разработка.
6. **W5** — решение «Activepieces в production или нет» по итогам W4 и ответа на L1–L3.
7. **W6** (если «да») — развёртывание Activepieces отдельным сервисом, подключения клиентов, мониторинг.
