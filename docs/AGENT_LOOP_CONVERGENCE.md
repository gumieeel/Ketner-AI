# Один цикл агента вместо трёх: ответ и предложение

Составлено 12.11.2026 по решению владельца (рантайм — свой цикл поверх `AIGateway`, Mastra не вводится). Статус — **предложение**; код ядра не писался.

## 1. Что есть сейчас (по коду)

| Путь                                                                     | Цикл?                                                                                                                                                                                  | Шаг модели (выбор модели, запасные, цена, учёт, списание)                                                                  | Метод провайдера                | Кто выполняет инструменты                                 |
| ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------- | --------------------------------------------------------- |
| `AgentGateway` — публичный `/v1` (`ai/agent-gateway.ts`, `routes/v1.ts`) | **Нет.** Один вызов модели с инструментами на запрос; цикл крутит клиент API                                                                                                           | Свой: цепочка запасных моделей, сторож (`AGENT_WATCHDOG_LIMITS`), правила тарифа и глубины, учёт в `api:<keyId>`, списание | `streamAgent`                   | Клиент API                                                |
| Ketner Code (`code/agent-runner.ts`)                                     | **Да:** шаги до `stepLimit`, ≤ 12 вызовов инструментов за шаг, ≤ 6 сбоев подряд, бюджет прогона, переход на модель дешевле (`continuationModel`), сжатие контекста (`compactMessages`) | **Свой третий:** перебор кандидатов, `computeRequestCost`, `credits.charge` на каждом шаге, учёт с `runId`/`step`          | `streamChat` (старый интерфейс) | Сервер: файлы проекта и песочница (`code/agent-tools.ts`) |

| Спайк `own-loop.ts` (ветка `claude/mastra-spike`)                        | Да, 60 строк                                                                                                                                                                           | `AIGateway` + `agentStep`                                                                                                  | `streamAgent`                   | Сервер                                                    |

Итог: **настоящий цикл сейчас один** (Ketner Code). Зато **шагов модели три**, и каждый по-своему выбирает модель, обрабатывает запасные, считает цену, пишет учёт и списывает кредиты. Вызов функций у провайдеров — тоже двумя интерфейсами: `streamChat` и `streamAgent`.

`own-loop.ts`, оставленный как есть, стал бы вторым циклом и четвёртым вариантом связки «шаг + учёт». Этого не делаем.

## 2. Предложение: одно ядро, общий шаг, разные инструменты

```
              ┌───────────────── ядро цикла (agent-core/loop.ts) ─────────────────┐
вход ──►      │ шаг → вызовы инструментов → проверка прав → выполнение → шаг … │ ──► итог + причина остановки
              │ лимиты: шаги, вызовы, время, кредиты за ответ/прогон; отмена   │
              └───────────┬──────────────────────────────┬──────────────────────┘
                          │ ModelStep                    │ ToolRegistry + политика
             AIGateway.agentStep (один шаг модели)   набор инструментов пути
             выбор модели, запасные, сторож,         бот: knowledge.search, lead.create, owner.notify
             цена, учёт, списание (T4.1)             Ketner Code: файлы, песочница, план
```

**Общее (одна реализация):**

1. **Шаг модели — `AIGateway` с `agentStep` (T4.1).** Единственное место, где выбирается модель, перебираются запасные, работает сторож стрима, считается цена, пишется `UsageRecord` и списываются кредиты (позже — по `effect_id` журнала кредитов). Метод провайдера — один (`streamAgent`); `streamChat` выводится после переноса Ketner Code.
2. **Ядро цикла — `agent-core/loop.ts`**, чистая функция без знания о боте или коде:
   - `step` — функция шага, в production это `AIGateway.agentStep`;
   - `tools` — реестр: схема входа (Zod), проверка прав (`platform/risk.ts` и разрешения), выполнение; ошибка инструмента превращается в результат для модели, а не в падение цикла;
   - `limits`: `maxSteps`, `maxToolCalls`, `maxToolCallsPerStep`, `timeoutMs`, `maxConsecutiveFailures`, **потолок кредитов на ответ и на прогон**. Ядро передаёт в каждый шаг остаток потолка как `maxChargeUsd`, поэтому два шага бота вместе не превышают 30 кредитов;
   - крючки: `prepareMessages` (сжатие контекста Ketner Code), `onLimit` (переход на модель дешевле или остановка), `onEvent` (поток в интерфейс, журнал `execution_events`);
   - причины остановки — закрытый список: `answer`, `escalated`, `max_steps`, `max_tool_calls`, `budget`, `timeout`, `cancelled`, `failures`, `error`.
3. **Различается только конфигурация:**

   |                           | Бот / агент платформы                       | Ketner Code            |
   | ------------------------- | ------------------------------------------- | ---------------------- |
   | Инструменты               | Действия из `AgentSpec.allowedActions`      | Файлы, песочница, план |
   | Лимиты                    | Из `AgentSpec.limits`; 30 кредитов на ответ | Свои                   |
   | Сжатие контекста          | —                                           | Есть                   |
   | Переход на модель дешевле | —                                           | Есть                   |
   | Учёт                      | `kind: 'assistant'` / `'agent'`             | `kind: 'code'`         |

**`/v1` (`AgentGateway`) циклом не становится:** по контракту API инструменты выполняет клиент. Он переходит на общий шаг — делегирует `AIGateway.agentStep` и сохраняет свой контракт: правила тарифа и глубины, учёт в `api:<keyId>`, формат OpenAI. Своя цепочка запасных моделей и учёт в нём исчезают.

остаток потолка, новый шаг не начинается при остатке меньше 0,0005 $. Учёт каждого шага — как у
обычного запроса шлюза (полная цена в учёте, списание не больше потолка шага).

ответ дороже ответа в один шаг. Потолок ответа не меняется. Замер до включения флага для клиентов —
отдельный шаг.

## 6. До включения флага (14.11.2026, в ветке, флаг выключен)

### 6.1. Ответ после лимита (3a)

**Было:** при остановке `max_steps`, `max_tool_calls`, `budget` или `failures` владелец уже заплатил
за шаги, а посетитель получал «Не получилось ответить…» (сообщение с ошибкой). Оставить так нельзя
по цифрам. Промпт бота с полными знаниями — около 9 тыс. символов (~3–4 тыс. токенов вместе с
историей), ответ — до 600 токенов. Один шаг стоит примерно:

| Цена модели за 1 млн токенов (вход / выход) | Шаг ~4 тыс. на входе, ~200 на выходе | Сколько шагов вмещает потолок 0,03 $ |
| ------------------------------------------- | ------------------------------------ | ------------------------------------ |
| 0,10 / 0,50 $                               | ≈ 0,0005 $                           | ~60                                  |
| 0,30 / 1,20 $                               | ≈ 0,0014 $                           | ~20                                  |
| 2 / 10 $                                    | ≈ 0,010 $                            | 3                                    |
| 4 / 20 $                                    | ≈ 0,020 $                            | 1,5                                  |

С моделями уровня 2/10 $ и дороже два-три шага с инструментами исчерпывают потолок: прежнее поведение
— 30 кредитов владельца и ошибка посетителю.

**Стало (`LoopRun.finalAnswer`, бот включает):** вместо такой остановки — ещё один шаг с
`toolChoice: 'none'`. Модель отвечает из того, что успела найти, посетитель получает ответ и форму
контакта. Бюджет на этот шаг резервируется. Первый шаг получает весь потолок, поэтому ответ в один
шаг ограничен так же, как на прежнем пути. Со второго шага шаг с инструментами может списать не больше
`остаток − max(0,0005 $, самый дорогой шаг прогона)`. Последний шаг входит в `maxSteps`. Итог: не
больше `maxSteps` вызовов модели и не больше 0,03 $ на ответ. Причина остановки в журнале остаётся
прежней (`max_steps`, …), а `output_meta.finalStep = true`. Ответа нет только в двух случаях: первый
шаг съел весь потолок (одна модель дороже ~0,03 $ за шаг) или последний шаг упал. Тогда — как раньше:
сообщение об ошибке и форма контакта.

### 6.2. Журнал: обращения к базе и задержка (3b)

Замер — `apps/mock-api/src/scripts/measure-journal-overhead.ts`: модель поддельная и мгновенная,
журнал в Postgres 16, 30 ответов на сценарий, медианы; `rtt` — добавленная задержка на каждое
обращение (сеть до базы). В счёт не входит первый ответ процесса для решения и версии: включение
агента там занимает ещё 2–3 обращения.

| Сценарий                     | rtt, мс | До: обращений до ответа | До: мс до ответа | После: обращений до ответа / всего | После: мс до ответа | После: мс всего (фоном) |
| ---------------------------- | ------- | ----------------------- | ---------------- | ---------------------------------- | ------------------- | ----------------------- |
| Ответ в один шаг             | 0       | 10                      | 12,7             | 1 / 3                              | 2,0                 | 6,1                     |
| Ответ в один шаг             | 5       | 10                      | 72,0             | 1 / 3                              | 7,3                 | 22,4                    |
| Ответ в один шаг             | 20      | 10                      | 226,7            | 1 / 3                              | 23,0                | 68,5                    |
| Поиск в знаниях, затем ответ | 0       | 16                      | 15,8             | 1 / 3                              | 2,1                 | 6,6                     |
| Поиск в знаниях, затем ответ | 5       | 16                      | 105,2            | 1 / 3                              | 7,4                 | 22,5                    |
| Поиск в знаниях, затем ответ | 20      | 16                      | 353,6            | 1 / 3                              | 22,7                | 68,6                    |

До ответа остаётся только то, что обязано быть до него:

- начало исполнения — ключ идемпотентности не даёт ответить дважды;
- включение агента — кэш процесса на 5 минут по владельцу, решению и версии;
- резерв эффекта внешнего действия (`reach: 'external'`) перед его выполнением.

Остальное (эффекты, события, итог) пишется пакетом после ответа, двумя командами. Сначала новые
эффекты в `reserved` и события, затем их итоги и итог исполнения. Одной командой нельзя: триггер
`execution_effects_guard` требует, чтобы эффект появился как `reserved`.

**Исправлено попутно:** JSON-параметры журнала передавались как `$n::jsonb`. Драйвер postgres.js
кодировал строку ещё раз, и в `spec`, `input_meta`, `data`, `result_meta`, `output_meta`, `error`
попадали JSON-строки вместо объектов. Проверка `spec ->> 'specVersion' = '1'` при этом проходила
впустую: `->>` у строки даёт NULL. Теперь параметры передаются как `$n::text::jsonb`, как в остальных
хранилищах; тест на Postgres проверяет `jsonb_typeof = 'object'`. Касалось только этой ветки: журнал
в `main` и в production не попадал.

### 6.3. Зависшие исполнения (3c)

Если пакет после ответа не записался (база недоступна, процесс остановлен), исполнение остаётся в
`running`. Reaper (`platform/execution-reaper.ts`) закрывает такие исполнения:

- **порог:** возраст от `started_at` не меньше max(10 мин, 5 × самый длинный срок прогона
  AgentSpec = 120 с), по умолчанию 15 мин. Живой прогон ядро прерывает по сроку (у бота 60 с), поэтому
  идущий прогон под порог не попадает;
- **объём:** не больше 50 исполнений за проход, раз в 5 минут; проходы не накладываются;
  `FOR UPDATE SKIP LOCKED`;
- **итог:** статус `failed`, причина `error`, `error = {"code":"reaped_stale_running"}`. Внутренние
  эффекты в `reserved` становятся `failed` (`before_dispatch`). Внешние в `dispatched` не трогаются:
  их исход неизвестен, их сверяют отдельно;
- **поздний итог** самого прогона закрытое reaper'ом исполнение не переписывает: `finish` и пакет
  меняют только `running`.

Запускается вместе с путём платформы: флаг не `off` и журнал в Postgres.

### 6.4. Ошибки инструментов (3d)

Модель видит только закрытый список сообщений `TOOL_ERROR_MESSAGES`: `unknown_tool`, `not_allowed`,
`invalid_json`, `invalid_arguments`, `tool_failed`, `tool_timeout`, `too_many_calls_in_step`,
`not_executed`. Текст исключения, адреса, пути и подробности разбора аргументов уходят только в
события прогона и в журнал: событие `error`, `result_meta.error` эффекта. Они очищаются от секретов
до записи. У вызова инструмента свой срок — у бота 5 с.

### 6.5. Замер на настоящей модели (3e) — запускает владелец

Скрипт: `apps/mock-api/src/scripts/measure-bot-paths.ts`, логика —
`apps/mock-api/src/scripts/bot-path-measurement.ts`. Одни и те же записанные диалоги (по умолчанию
20, по 3 вопроса посетителя) проходят оба пути. История каждого вопроса — записанная, поэтому вход у
путей одинаковый. Порядок путей чередуется.

Что пишется в сводку:

- себестоимость и кредиты;
- шаги и вызовы инструментов;
- причины остановки и случаи последнего шага;
- задержка p50 и p95;
- модели;
- сходство ответов и расхождения формы контакта;
- таблица ходов.

Ограничения скрипта:

- **флаг:** `BOT_PLATFORM_RUNTIME` должен быть ровно id этого решения, `all` и списки отклоняются;
- **база:** подключение только для чтения, проверяется `SHOW transaction_read_only`;
- **деньги:** кредиты, учёт и журнал — в памяти, владельцу ничего не списывается. Расход у провайдера
  настоящий: худший случай печатается до запуска;
- **без `--yes`** — только выбор диалогов и оценка расхода.

Проверено здесь без настоящей модели:

- тесты логики;
- отказ при неверном флаге и без ключей провайдера;
- полный прогон на 3 диалогах через настоящий шлюз и HTTP-провайдер с поддельным сервером OpenRouter.

Цифры поддельного сервера ничего не говорят о стоимости.
