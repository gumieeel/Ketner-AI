## 1. Итог

- В production RLS включён на **всех** таблицах `public`, политик и представлений в `public` нет, а сервер работает ролью-владельцем с BYPASSRLS. Поэтому строки через API Supabase сейчас **не читаются и не вставляются** (проверено владельцем 11.11.2026).
- Лишнее — права `anon` и `authenticated`, которые Supabase выдаёт по умолчанию:
  - **`TRUNCATE`**: на него RLS не действует. Через Data API (PostgREST) `TRUNCATE` не выполнить, поэтому сейчас это вторая линия защиты, а не открытая дыра;
  - права по умолчанию: каждая **новая** таблица снова получит всё. Если её создать без RLS, данные сразу откроются через Data API.
- Ketner этими ролями не пользуется. В репозитории нет клиента Supabase (`@supabase/*`, ключа `anon`, `SUPABASE_URL`): вход через Better Auth, к базе обращается только сервер через `DATABASE_URL`.
- Исправление снимает права и меняет права по умолчанию. **RLS не трогает.** Проверено на одноразовом кластере по модели production (раздел 5).
- **Резервных копий нет.** Применять что-либо к production можно только после проверенной копии (раздел 7).

## 4. Исправление

[SECURITY_REMEDIATION_PROPOSAL.sql](SECURITY_REMEDIATION_PROPOSAL.sql), выполняется ролью `postgres` одной транзакцией (`psql -1 -v ON_ERROR_STOP=1`):

1. **Предусловие.** Текущая роль — владелец каждой существующей таблицы и функции из списков. Иначе исключение, и ничего не меняется.
2. **Прежнее состояние.** Права `anon`/`authenticated`/`PUBLIC` по каждой таблице и функции и права по умолчанию записываются в `security_remediation_state`. Повторный запуск запись не перезаписывает.
3. **Таблицы:** `REVOKE ALL ON TABLE … FROM anon, authenticated`.
4. **Функции приложения** (`solutions_legacy_template()`): `REVOKE EXECUTE … FROM PUBLIC, anon, authenticated`. Это триггерная функция: при срабатывании триггера право `EXECUTE` не проверяется, сервер (владелец) его сохраняет.
5. **Права по умолчанию** для объектов, которые создаёт `postgres`:
   - `IN SCHEMA public`: `REVOKE ALL ON TABLES`, `ON SEQUENCES`, `ON FUNCTIONS FROM anon, authenticated`;
   - **глобально** (без `IN SCHEMA`): `REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC`. Встроенное право `PUBLIC` на функции — глобальное, отозвать его для одной схемы PostgreSQL не позволяет. **Следствие:** функции, которые `postgres` создаст в любой схеме, не будут доступны `PUBLIC` без явного `GRANT`. Объекты, которые создаёт `supabase_admin` (расширения, служебные функции Supabase), это не затрагивает: у него свои права по умолчанию.
6. **Самопроверка.** Если хоть одна проверка не прошла — исключение, и вся транзакция откатывается:
   - на таблицах из списка нет ни одной записи прав `anon`/`authenticated`/`PUBLIC`;
   - `has_table_privilege` для обеих ролей возвращает false — на PostgreSQL 17 с `MAINTAIN`;
   - функции из списка не вызываются `anon`/`authenticated`;
   - пробные таблица, последовательность и функция, созданные внутри транзакции, не получают их прав. Это ловит права по умолчанию, заданные глобально или другой ролью.

Чего не делает:

- не включает и не выключает RLS — в production он уже включён (таблицы без RLS только перечисляются в `NOTICE`);
- не включает `FORCE`, не создаёт политик;
- не меняет права `service_role` и владельца, не меняет данные.

Повторный запуск безопасен.

Ограничения:

- **Права на отдельные колонки** снимаются вместе с правами на таблицу, а откат их не вернёт. Если такие есть, скрипт сообщает об этом в `NOTICE`; у ролей API в Supabase их обычно нет — проверить по R1 (`column_grants`).
- **`rls_auto_enable()`** — событийный триггер production (R3): скрипт его не трогает и перечисляет в `NOTICE` как функцию вне списка, доступную `anon`. Вызвать её через Data API нельзя: функции событийных триггеров вызываются только как триггеры. Миграции Ketner всё равно включают RLS явно (`ENABLE ROW LEVEL SECURITY`): поведение не должно зависеть от настройки проекта Supabase.
- Создание таблицы в Supabase запускает событийные триггеры (`pgrst_ddl_watch` — PostgREST перечитает схему; `rls_auto_enable` — RLS на пробной таблице). Это безвредно: пробные объекты удаляются в той же транзакции.
- Права по умолчанию `supabase_admin` в `public` не меняются: это объекты Supabase.

Пояснения:

- **Порядок записей прав.** После `REVOKE` и повторного `GRANT` PostgreSQL добавляет запись роли в конец списка: права те же, порядок другой. Поэтому сырой каталог отличается в 80 строках, а нормализованный (записи отсортированы, [normalize-acl.mjs](security-review/normalize-acl.mjs)) совпадает.
- **Сортировка снимка каталога.** У трёх ограничений `discovery_budget_reservations` одинаковое сокращённое имя, и снимок, отсортированный только по имени, мог менять их порядок. В `persistence-review/catalog-snapshot.sql` добавлена сортировка по свойствам.
- **Тесты используют свои схемы.** Набор создаёт свою схему на каждый тест, поэтому права в `public` его не касаются. Что сервер работает с таблицами `public` после исправления, доказывают смоук-тесты через API и старт сервера.

## 6. Решено и что остаётся

1. **Последовательности** — в объёме: права по умолчанию `ON SEQUENCES` в `public` снимаются у `anon`/`authenticated` (иначе новая последовательность дала бы им `setval`). Существующих последовательностей в `public` нет (R3).
2. **Функции** — в объёме:
   - `solutions_legacy_template()` — `REVOKE EXECUTE` у `PUBLIC`, `anon`, `authenticated`;
   - права по умолчанию на функции — раздел 4, шаг 5;
   - функции предложения платформы (`platform_contains_secret`, `platform_append_only`, `executions_insert_refs`, `execution_effects_guard`) отзывают `EXECUTE` сами, сразу после создания ([PERSISTENCE_MIGRATIONS_PROPOSAL.sql](PERSISTENCE_MIGRATIONS_PROPOSAL.sql)); проверка — `persistence-review/function-privileges.sql`.
3. **Data API.** Если он не нужен (Ketner его не использует), можно убрать схему `public` из открытых в настройках Supabase. Это изменение конфигурации проекта, не базы; рассматривает владелец.

## 7. Порядок выката (обязательная проверенная копия)

В проекте (Supabase Free plan) **нет резервных копий**. Ни одна миграция — это исправление, `0013`+ и любые другие — не применяется к production без шагов 1–4.

**1. Запросы только для чтения.** R1–R5 выполнены 11.11.2026 (раздел 2); перед выкатом повторить R1 и R2, чтобы убедиться, что ничего не изменилось. Production — PostgreSQL 17.6, поэтому `pg_dump` и `pg_restore` версии **17** (или новее), кластер проверки восстановления — тоже 17.

**2. Копия и отпечаток из одного снимка.** База — 21 MB (R5): копия и восстановление занимают секунды. Подключение — прямое (`db.<ref>.supabase.co:5432`) или пулер в режиме сессии. Пулер в режиме транзакций (порт 6543) не подходит. Пароль вводится по запросу `psql`/`pg_dump` или через `~/.pgpass`; в команды и чат его не вставлять.

Терминал A — сессия держит снимок открытым:

```
psql "host=… port=5432 dbname=postgres user=postgres sslmode=require" -X -tA
BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY;
SELECT pg_export_snapshot();          -- скопировать идентификатор снимка
```

Терминал B — копия всей базы из этого снимка (не закрывая терминал A):

```
pg_dump "host=… port=5432 dbname=postgres user=postgres sslmode=require" --snapshot=<идентификатор> -Fc -f ketner-<дата>.dump
```

Снова терминал A — отпечаток из того же снимка, затем закрыть транзакцию:

```
\pset fieldsep '|'
\o production-fingerprint.txt
\i docs/security-review/table-fingerprint.sql
\o
COMMIT;
```

**3. Проверка восстановления на одноразовом кластере PostgreSQL 17** (как production):

```
PGBIN=/usr/lib/postgresql/17/bin bash docs/security-review/verify-restore.sh ketner-<дата>.dump production-fingerprint.txt
```

Нужно получить `restore: OK` и `PASS restored copy matches production fingerprint`.

- Восстанавливается схема `public`; схемы Supabase остаются в копии для восстановления в Supabase.
- При `FAIL` — остановиться, ничего не применять.
- Копию хранить вне Supabase и вне репозитория: в ней пользовательские данные и секреты.

Эти шаги отрепетированы на одноразовом кластере (раздел 5): снимок, запись после него, копия, восстановление, совпадение 40 таблиц.

**4. Только после `PASS`:** в окно с малой нагрузкой выполнить ролью `postgres`:

```
psql "…" -X -1 -v ON_ERROR_STOP=1 -f docs/SECURITY_REMEDIATION_PROPOSAL.sql
```

При любой ошибке транзакция откатывается целиком.

**5. Проверка после применения:**

- повторить R1 и R2: у `anon`/`authenticated` прав нет; в R2 для `postgres`/`public`/`r` их тоже нет;
- проверить сайт: вход, список решений, чат.

**6. Откат при проблемах:**

```
psql "…" -X -1 -v ON_ERROR_STOP=1 -f docs/SECURITY_REMEDIATION_ROLLBACK.sql
```

Откат возвращает права ровно такими, какими они были.

## 8. Ошибки в `main`, найденные попутно

Ошибка 1 исправлена в ветке (не в `main`): [NODE_STARTUP_FIX.md](NODE_STARTUP_FIX.md). Ошибка 2 не исправлена.

1. **Сервер не стартует на Node ≥ 22.13 с `DATABASE_URL`.**
   - Причина: `initAuthDatabase` (`auth/better-auth.ts`) при доступном `node:sqlite` вызывает Better Auth `getMigrations`, а тот для адаптера drizzle вызывает `process.exit(1)` (`better-auth/dist/db/get-migration.mjs`) — `try/catch` это не ловит.
   - Воспроизведено на Node 22.23.4: сервер завершается с кодом 1 до `listen`. На стенде он запускается с `--no-experimental-sqlite`.
   - `package.json` требует `node >= 22.12.0`, а `node:sqlite` доступен без флага с 22.13. Production работает, значит Render, видимо, использует 22.12 или другую сборку — **не проверено**. Риск: обновление Node на Render остановит сервер.
2. **Демо-пользователь в Postgres не может войти.** `db/sync.ts` записывает хеш `4578b6…`, а `pbkdf2('password123', соль из нулей)` даёт `bbc0bc…`. Вход демо-аккаунтом при `DATABASE_URL` возвращает `500 demo_unavailable`. В production демо отключён, затронуты только разработка и стенды.
